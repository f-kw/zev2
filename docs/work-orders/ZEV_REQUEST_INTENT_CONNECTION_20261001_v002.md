## 1. 監査判断

通常の下書き・承認後7命令に目的全文、素材URI、編集条件が保存されることと、Digest判断が呼ばれることは別。checkpointの報告・probe・通常factory・構成builderを照合し、この切り分けを受理する。通常テーマは目的を使わず、通常構成は探し直し指示だけを読む。通常factoryにはDigestの探索・比較採否・内部保持を呼ぶ箇所がない。接続工事全体を完了扱いにしない。

既存通常経路はテーマ成果物と人間のテーマ選択を前提とし、Digestは複数候補の機械採否・保持計画を持つ。**両者の保存物・承認を同一視してはいけない。** 今回は通常callerからDigest計画を別記録として生成・保存する接続を成立させ、通常出力への採用・製造にはまだ接続しない。人間のテーマ選択を毎回求める新しい工程を追加するものでもない。

## 2. 呼出し位置と実行条件

2. 同factoryのruntime依存に、明示的に渡すDigest計画準備用の任意依存を追加してよい。依存を指定した場合のみ、runner配下の具体的executorが既存の探索→比較採否→内部保持を呼ぶ。入力生成・保存・検査を丸ごと試験callbackへ差し替えず、差し替える判断providerは通信しない試験実装に限る。具体的な型名・小さい関数分割はCodexに任せる。
3. 通常起動の既定は依存未指定のまま。`index.ts`の本番runtime、環境変数、API、UIから自動有効化しない。必要なruntime構築の接続変更だけは許可するが、新しい公開mode・別runner・別キューは作らない。purposeの単語、preset、素材ID、保存pathの偶然からDigestモードを推測しない。
4. 依存未指定なら既存の入出力・人間確認・副作用は不変。指定した隔離試験では同じ通常factoryのbranchを実行し、計画を保存した後も既存のテーマ成果物の意味を変えない。Digest準備で不正・失敗・中断が起きた場合は、その実行を成功にせず既存の失敗経路へ返す。失敗を握りつぶして旧結果で代替しない。
5. この段階の成果は **「明示した準備依存を使う通常factoryから、承認済み依頼に結び付いたDigest計画を作れる」** こと。通常UIからDigest完成動画を作れる、本番で自動選定が有効になった、通常全工程E2Eが完成した、とは報告しない。

## 4. 保存と再開に許可するもの

承認済み通常命令と既存Digest保存物の対応付けを実装する。新しい汎用storeや新しい公開保存契約は作らない。

- 保存先は、既存のrequestごとのartifact領域の配下に分離したDigest準備領域とする。試験では隔離runtimeだけを使う。依頼IDと入力束縛の違いで他実行へ混入しないようにする。既存のテーマ・構成・前回Digest媒体や入力を上書きしない。
- 既存版の探索要求／回答／結果／候補集合、採否要求／回答／受理、保持要求／回答／解決結果を再利用し、各段階の実入力から要求SHAを計算して保存する。前回実験の素材・目的・件数・尺・回答を通常既定へ固定しない。旧回答の要求SHAを新しい要求へ付け替えて正当化しない。
- **追加してよい内部情報は通常命令とこれら既存保存物を結ぶ記録に限る。** 既存のplan/receiptで表現できれば再利用する。不足する場合は、小さい版付き内部binding記録を一種類だけ定義してよい。役割は出所・対応・再読であり、公開APIやtheme/compositionのschemaの代替ではない。
- その記録に必要なものは、通常のrequestDraftId／AgentRequest ID、承認下書きと命令の入力snapshot・SHA、素材URI／source ID／元動画・文字起こし・共通発話の実参照とSHA、既存の編集条件・policy、3判断の要求／回答／結果参照、実行実装の参照、準備の完了／未完了の区別。承認は文字列の`approved`を置くだけで成立させず、通常stateの該当下書き・命令・依存成果の実際の対応と整合を検証する。
- 文字起こしと共通発話の間は既存変換・出所検査を使う。同じURIというだけで別の本文やIDを受理しない。素材の取得・STT・原文訂正・時刻再計算方式の変更は行わない。
- purposeは通常命令に保存された全文を探索と採否の`productionRequest`、保持の`taskDescription`へ渡す。保持用の既存指示を添える場合も全文を欠落させない。既存の編集条件は出所とともに保持し、未定義の文字列を候補数・尺の独自強制規則へ変換しない。別目的・別条件・別素材・別承認版の記録を使い回さない。
- 再開は保存済み段階を実SHAと既存validatorで再読し、未完了の次段階から扱えることを確認する。同一入力の完全保存があればprovider再呼出しは不要。読み取り確認と実行資格を分け、再読だけでキューや人間承認を変更しない。未知版、不正参照、欠損、未完了、改変、旧要求に束縛された回答を拒否し、完了に見せかけない。
