## 3. 実施範囲

1. 通常の依頼入力・下書き保存・承認後命令・実際のrunner／executor・各判断request builderを辿り、制作意図がどこからどの欄へ渡るかを短い対応表にする。既存の通常経路と検証専用経路を明確に分ける。受渡しが既に成立する部分は利用する。
2. 欠落・固定文への置換・誤った依頼の参照があれば、既存経路の該当箇所だけ修正する。通常入力の `purpose` 等を優先し、同じ意味の第二入力欄や新UIを作らない。新しい接続helperが必要なら通常callerから実際に呼び出し、検証スクリプトの中だけで完成させない。
3. 制作意図は明示入力から渡す。前回のホラー用文面、素材ID、7採用／9保持、15分23秒を製品の固定値・既定値にしない。既存の編集条件や承認・素材参照を落とさず、意味を変える勝手な要約・係数・選定規則を追加しない。
4. 保存済み素材と既存の受理方式を用い、通常入力から各判断の呼出し直前までを実行し、実際に渡った入力を捕捉する。必要なら判断providerだけを通信しない試験用実装へ差し替える。通常のrequest builderまで試験用に作り直さない。
5. 保存・再起動・別process再読で同じ依頼の意図と参照が復元されることを確認し、変更箇所の試験・関連type-checkを行う。必要な最小の変更で結合が成立したら、下記の保存・報告まで進む。

新しいAPI schemaや保存契約の意味の変更、通常runner全体の新設・全工程統合が必要な場合は本書の範囲外。どの接続が無いかと最小差分を保存してGPT_DECISIONへ返す。型だけ新設したり、未接続のhelperを通常経路完成と報告したりしない。

## 4. 接続試験の完了条件

- 通常の依頼入力から探索・採否・保持の実際の入力へ制作意図が届く。承認後の依頼ID・素材参照・保存版との対応を示す。
- 意図を変えた別の試験入力でも対応する各段階が更新され、前回素材や固定文・古い依頼へ戻らない。これは配線の試験であり、新しい製品方針や内容品質の比較ではない。
- 保持判断に必要な全体の意図が欠落しない。既存の条件・根拠・ID集合／被覆・時刻解決は維持する。
- 入力を変えた後の古い回答や別素材の保存物を黙って再利用しない。request SHA不一致等は既存の拒否条件で検出する。古い回答を新しい依頼で生成したことにする付け替えはしない。
- 下書き未承認からの実作用、入力変更後の旧承認の使い回し、試験からの実キュー起動を起こさない。既存仕様上の拒否／未指定扱いを確認し、黙って新しい既定意図を補完しない。
- 外部API・素材取得・STT・動画生成を起動しない隔離されたローカル試験で成立を示す。通常UIの実操作、外部推論の品質、完成動画までのE2Eと混同しない。
