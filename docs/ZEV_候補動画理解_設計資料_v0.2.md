# ZEV 候補動画理解 設計資料

**v0.2 — 候補発見後の実動画理解と人間確認時間を分ける正本設計**

**確定日:** 2026-09-04
**状態:** 比較実験計画まで実装済み。API実行、広域探索動画、正式実走jobは未作成。

このv0.2を候補動画理解の現行設計正本とする。v0.1は当時の調査・未確定案を残す履歴であり、v0.2と異なる内容を現在の実行条件や判断根拠として使わない。

## 1. この設計で作ろうとしているもの

ZEVの目的は、見たものが気持ちいい動画を作ることである。Geminiを導入すること自体は目的ではない。

候補が見つかった後、現在は人間が比較的長い確認動画を見て、中心となる出来事、反応、必要な前提、自然な終わり、映像として成立するかを判断している。この負担を減らすため、候補周辺の限定された動画をGeminiに先に見せ、実映像・音声・発話から人間が最初に見るべき範囲を絞れるかを測る。

Geminiという有料工程を一段増やしても、人間が見る時間を無料方式より明確に減らせないなら採用しない。「動画内容を理解できた」というだけでは成功ではない。

## 2. 全体は3段に分ける

```text
第1段: 候補を見つける
  ↓
第2段: 候補周辺の限定動画をGeminiが観測する
  ↓
人間が必要範囲と採否を確認する
  ↓
第3段: 承認済み範囲を決定的に製造する
```

### 第1段 — 候補を見つける

ここでは、詳しく見る価値がありそうな地点と根拠を見つける。完成動画の区間は決めない。

候補の発見方法は一つに固定しない。通常切り抜き、コメント起点、将来の音量や画面変化、遠方接続、カタルシス、その他の方式がそれぞれ候補を出せる。どの方式から来た候補でも、その後は共通の候補動画理解へ渡せる構造を目標にする。

### 第2段 — 限定された候補周辺動画を理解する

Geminiには長尺配信全体を探索させない。ZEV側が候補地点の周辺だけを、元動画との対応を失わない比較的広い作業領域として用意する。

Geminiは、その中から次を観測する。

- 中心となる出来事。
- その出来事への反応。
- 出来事と反応が自然に終わる位置。
- 実映像で確認できる原因やきっかけ。
- 理解に本当に必要な最低限の前提。
- 外しても中心の出来事や反応を損なわない部分。ただし、これは除外候補の観測であり正式カットの決定ではない。
- 画面変化の弱さ、文章読み、メニュー操作、音声依存など、映像上の注意。
- 候補動画だけでは判断できない材料不足。

Geminiの回答は観測結果であり、正式な動画区間ではない。候補動画内の時刻として受け取り、ZEV側が厳密に検査して元動画へ投影した後、人間が確認する。

### 第3段 — 人間承認後に正式製造する

人間が範囲と採否を承認した後は、既存の決定的工程を使う。Geminiの推測で製造条件を補わない。

- 正式発話IDから時刻への変換。
- 元動画、入力、成果物のSHA束縛。
- source PTS mappingとframe mapping。
- base-media生成。
- 字幕対象の全量閉包。
- presentation instruction。
- renderer admission。
- renderer。
- 技術QC。

## 3. Geminiが持つ責務と持たない責務

Geminiの責務は、限定された候補周辺動画を実際に見て、必要そうな映像部分と確認できた事実を役割別に返すことだけである。

Geminiは次を決めない。

- 長尺配信全体からの候補発見。
- 良い動画かどうか、点数、順位、最終採否。
- 正式なカット境界。
- 遠方接続の意味関係。
- カタルシスの線。
- PTSやframe mappingの正当性。
- 正式発話、字幕閉包、renderer入場。
- rendererの結果や技術QCの合否。

Geminiが返した時刻がもっともらしくても、そのまま正式境界にはしない。実在するPTS mappingで投影できない部分を補間、丸め、許容値で埋めることも行わない。

## 4. 人間へ最初に見せる範囲

Geminiが返した情報を、最初から全部連結して人間へ見せない。初回確認の基本範囲は次の3役割だけである。

```text
中心となる出来事
  +
反応
  +
自然な終わり
```

これらの実在区間の和集合を、余白追加や隙間埋めをせず提示候補にする。原因と最低限の前提は結果として保持するが、初回から自動追加しない。外せる部分も初回提示には入れない。

人間が「これだけでは分からない」と判断した場合に限り、原因や前提を追加材料として検討する。この追加提示はまだ実装していない。

3役割のどれかを観測できなかった場合、その役割の区間を推測で作らない。初回提示を作れる状態にせず、提示区間も作らない。

この順序により、前提を足し続けて長い文脈の中では成立しているように見せる、旧区間化の問題を再発させない。

## 5. 探索領域を自動拡張しない

Geminiが「もっと前後が必要」と返しても、探索領域を自動で広げて再実行しない。自動retryや、自動の2回目探索も作らない。

- 中心となる出来事自体が見つからない場合は、候補発見が悪かった可能性を分離して調べる。
- 中心は確認できるが前提が足りない場合は、材料不足として保留する。
- 必要映像が最初の探索領域外だった場合は、Geminiの理解失敗ではなく探索領域の失敗として記録する。

将来、追加探索が本当に必要になった場合も、人間承認後の別工程として一回だけ行う案を検討する。現在の設計には含めない。

## 6. 無料方式を必ず対照にする

Gemini方式の価値は、Geminiを使わない短い人間確認と比べて測る。

現在の較正用無料baselineは、各候補地点の前後16,000msを取り、既存の正式発話境界へ外向きに広げた区間である。5本分の選択元動画区間を合計すると413,837ms、つまり6分53.837秒になる。

これは広域探索動画を人間へ見せる方式ではない。候補地点と既存発話境界だけから決定的に作り、人間へ直接提示する無料方式である。

前後16秒という値は、既知の人間正解を見ながら選んだ較正値である。前後15秒ではdoctor終端を落とし、前後20秒より短くできることまでを確認している。独立した性能値ではない。未使用validationでは変更せず使う。

## 7. Geminiだけが見る探索領域

現在の較正用Gemini探索領域は、各候補地点の前34,880ms、後15,378msを取り、既存の正式発話境界へ外向きに広げた区間である。5本分の選択元動画区間を合計すると543,592ms、つまり9分03.592秒になる。

この約9分04秒はGeminiだけが見る作業材料であり、人間確認時間には加算しない。Gemini方式で人間が見るのは、Gemini結果から作る「中心となる出来事＋反応＋自然な終わり」の最小提示候補だけである。

前34,880ms・後15,378msも既知の人間正解から導いた較正値であり、独立した性能値ではない。未使用validationでは変更せず、必要映像が外にあった場合も結果を見て広げて救済しない。

無料baselineとGemini探索領域は別々に外向きsnapする。無料側の後方16,000msはGemini側の後方15,378msより長いため、10地点中5地点では無料窓の終端がGemini窓より後ろになる。片方を他方へ包含させるためのunionや自動補正は行わず、二つの実在区間を別責務として保持する。

## 8. 最初の5本は較正である

最初の5本は、正式な導入判定ではなく、方式が狙った動きをするか確かめる較正・実現可能性確認に使う。

較正である理由は次のとおりである。

- 無料baselineを既知の人間正解から選んだ。
- Gemini探索領域も既知の人間正解から導いた。
- 結果を見てprompt、schema、探索窓、比較方法を直す可能性がある。

この5本では、役割別の観測が実映像に対応するか、中心・反応・自然な終わりを短く取れるか、既知の必要な瞬間を落とさないか、映像上の注意と材料不足を返せるか、PTS投影が安全に成立するか、人間確認時間を無料方式より減らせそうかを確認する。

先頭4本は人間承認済みの必要区間を持つ。必要な瞬間の包含は4本・8地点を分母にし、開始差と終了差は記録する。ただし境界差は、境界発見能力の合否には使わない。

5本目 `candidate-horror-game-to-screams-001` には、人間承認済みの正解区間がない。無料提示時間、Gemini実行、役割出力などの動作確認には含めるが、必要瞬間包含率や人間正解境界差の分母には入れない。存在しない正解は作らない。

較正中に何を変更しても、その5本の結果は正式性能証拠へ昇格させない。

## 9. 正式な導入判断は未使用validationで行う

較正が成立した場合だけ、設計やprovider観測に一度も使っていない別候補でvalidationを行う。「未使用」とは、較正、protocol設計、過去のprovider観測のどれにも使っていないことをいう。

未使用validationの最初のprovider送信前に、次を全て凍結する。

- 無料baselineの前後16秒と外向きsnap。
- Gemini探索領域の前34,880ms・後15,378msと外向きsnap。
- promptとresponse schema。
- modelとstatic処理。
- thinking level、1 FPS、media resolution。
- JSON応答形式と可視回答上限。
- 全validation候補をFiles APIで扱う動画transport。
- 比較指標。

全候補のraw provider response SHAとcanonical result SHAが固定されるまで、人間正解を開かない。一件ずつ先に答え合わせすることも禁止する。

結果を見た後でbaseline、探索窓、prompt、schema、初回提示方法、比較指標などprotocolのどこかを変えた場合、その集合はvalidationではなくcalibrationへ降格する。変更後の方式を評価するには、さらに別の未使用候補が必要になる。

## 10. 導入条件

導入条件の中心は、必要な瞬間を保持しながら、人間が見る時間を無料baselineより明確に減らすことである。

現在、何秒または何パーセント減れば「明確」とするかは決めていない。独自の係数、重み、合成点、事後的な合格線は作らない。較正では実際の提示尺をそのまま測り、未使用validationへ進む前に比較指標を凍結する。最終採否は人間が行う。

## 11. 失敗を正しく分ける

同じ「候補を作れなかった」でも原因を混ぜない。

| 分類 | 意味 |
| --- | --- |
| candidate discovery failure | 最初の候補発見が悪く、見るべき出来事へ到達していなかった |
| exploration window failure | 必要な映像がGeminiへ渡した範囲に入っていなかった |
| video understanding failure | 必要映像は範囲内にあったが、Geminiが正しく観測できなかった |
| projection / manufacturing failure | 観測後の時刻投影、mapping、媒体製造などで失敗した |

これらとは別に、「技術的には成立したが、人間が動画として良くないと判断した」という結果を保持する。これは技術失敗にもGemini失敗にも書き換えない。

## 12. 音量・コメント・画面変化センサー

音量、コメント量、画面変化などのセンサーは現時点では実装しない。

将来使う場合も、良い動画を採点する総合スコアにはしない。候補を見つける補助、またはGeminiへ渡す探索領域を十分広く取る補助として、それぞれ独立した観測を保持する。独自係数で単純合成しない。

## 13. 遠方接続へ使う場合

遠方接続への接続は今は実装しない。将来は次の順序を基本とする。

```text
後半候補を見つける
  ↓
後半周辺をGeminiが実動画理解する
  ↓
後半の核心を人間が確認できる状態にする
  ↓
その後半を参照して前半を意味探索する
  ↓
前半周辺をGeminiが実動画理解する
  ↓
人間が「後半だけ」を見た後、「前半＋後半」を確認する
```

Geminiは前半と後半の意味関係を決めない。前半・後半を独立に最短化すると、関係が成立するための前提や回収を失うため、二つを別々に短縮する設計にはしない。

## 14. カタルシスへ使う場合

カタルシスへの接続は凍結する。3〜4場面を個別に短くすると、線として必要な溜めを失う可能性がある。

将来は、個別場面の実動画理解と、複数場面を通した線全体の理解を分ける二段構成が必要になる可能性だけを記録する。人間確認済みの正例が3本以上揃うまで、詳細設計や実装へ進まない。

## 15. 決定的製造は置き換えない

Geminiで置換を検討するのは、候補発見後に人間が行ってきた発見的な区間化判断と、映像適性の一次確認である。

発話IDから時刻への変換、SHA binding、source PTS mapping、frame mapping、base-media、字幕全量閉包、renderer admission、renderer、技術QCは置き換えない。人間の最終採否と、人間が見る確認媒体も残す。

Geminiが観測するためだけに作る中間review媒体は将来減らせる可能性があるが、人間最終確認用の動画をなくす理由にはしない。

## 16. 実験の公平性と保存

比較実験計画はローカル専用とし、provider入力へ送らない。providerへ送る入力には、人間評価pathやSHA、人間の採否と理由、正解区間、説明的なcandidate IDやfilenameを含めない。

将来の正式実走では、候補ごとのFiles API付随通信と推論通信を、一つの順序付きtransport recordへ閉じる案を第一候補とする。ただし、送ったもの、返ったもの、通信順、回数、HTTP status、payload SHA、動画SHA、失敗位置を独立検証できなければならない。秘密headerとupload session URLは保存しない。

正式実走の成果物構成は、成功時37 path、最悪時43 pathを第一候補としているが、生成着工はまだ承認されていない。

## 17. 現在固定している実験条件

較正実験を実走する場合の現在の条件は次である。ただし、これは通信承認ではない。

- modelは `gemini-3.8-flash`。
- static video understanding。
- 1 FPS、高media resolution、medium thinking。
- JSON Schemaによるstructured output。
- 可視回答の上限は1件4,096 tokens。
- 5本全てをFiles APIで扱い、1動画につき1推論、合計5推論。
- retry 0、repair 0。
- providerへ見せるfilenameやdisplay nameには候補の意味を入れない。

送信前にexact request、input token数、入力費用、可視回答上限、最大推論回数、Files API付随通信を固定する。medium thinkingのtoken数は事前に厳密固定できないため、thinking込み総費用を実行前のexact値とは表現しない。実行後にprovider usageと価格snapshotから推定総費用を計算し、実請求額とは区別する。

## 19. 次に進む場合

この設計資料と準備実装を固定した後は停止する。

次に進むなら、別のkawafmm裁定を受けて、現在の5候補についてGeminiだけが見る広域探索動画5本を作り、各動画の全区間を正式なsource PTS mappingへ閉じる実験準備を行う。その後にも、正式job、Files APIとcountTokensとGemini推論のtransport、exact requestと費用preflight、human trust anchor、comparison result verifier、37/43 pathの正式成果物構成、API実走承認が必要である。

この文書の固定だけでは、動画生成、外部通信、費用支出、正式job生成、main workflow接続を許可しない。
