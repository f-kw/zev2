## 13. 作業中に判断が必要になった場合

この指示の目的に収まる通常の設計選択、具体的な有限値、必要なファイル構成、代表配色、関連試験、局所修正はCodexへ委任します。

微細な仕様ごとに本人へ質問しません。

一方、次の境界に当たった場合は、その操作だけを止めます。

* 新規費用
* 外部への動画・音声・画像送信
* 新素材・依存・モデル取得
* 正式trust・契約変更
* 原版置換
* main merge
* tag
* release
* ショート着工

通常審査が拒否した操作は、別path・別担当・別手段で迂回しません。

既存の相談役へ、問題の差分・必要な判断・独立して進める部分をまとめて相談してください。

本人の新しい決定が不可欠な場合だけ、その事項を一つにまとめて残します。

一つの未解決を理由に、作業可能なR1〜R3を全体停止しないこと。

## 14. 保存・報告・終了条件

工程ごとに必要なcheckpointを保存して構いません。

原資料を削除・移動せず、生成動画・PNG・PCM・巨大logは管理済み出力へ置き、必要なsource・試験・軽量記録を選別してcommit／pushします。

既に整理した未管理データの全量棚卸しには戻りません。

今回の生成物のGit流入と、必要sourceがignoreに隠れていないことを確認します。

最終報告では、各要望を次の状態へ分けて示してください。

* 実装・技術確認済み
* 原因確認の結果変更不要
* 根拠不足でその一件のみ未了
* 審査等でその操作のみ保留
* 人間の修正後確認待ち

報告の中心は次です。

* どの指摘を、どう修正したか。
* 実際の短尺・統合候補のどこで確認できるか。
* 未了があるなら、その具体的な不足は何か。
* 旧回答・原版・対象外のどこを保持したか。
* 帰宅後に見る一つのレビュー入口はどこか。

R1の報告だけで終わらず、今回許可したR2・R3・統合確認まで、実施可能な部分をすべて進めてからまとめて監査へ戻ってください。

途中で相談役の判断を受けた場合も、その範囲を反映して続行します。

全範囲が終わった後は、新しい工事を独断で増やさず、同じZEV Build Loopへ最終監査を依頼します。

「Codexです。」は相談役への直接報告だけに付け、本人向け報告には付けません。

今回は、作業量を増やすための基盤・帳票・比較案ではなく、受領済みの指摘を実物へ反映することを優先してください。

帰宅後に、まとまった修正版を変更ポイントだけで確認できる状態を目指します。
