## 1. 今回、何を変更するか

従来の工程I〜IVで整えた、字幕表現・接続表現・自動配置・一件後修正は、今後の品質改善に使う土台として維持する。

**機能の技術完成と、出力される動画の品質が十分であることは別に扱う。** ただし、人間レビューが溜まっていること自体を失敗とせず、回答を正しく蓄積・反映できる状態で開発を進める。固定済みの人間レビュー運用を引き継ぐ。

| これまでの主眼 | 新計画での主眼 |
|---|---|
| 表現の種類を揃える | 既存表現の完成度と、使いどころを良くする |
| 自動配置して動画が出ることを確認する | 実際の出力から、不適切な配置・不足・改善余地を見つける |
| 技術完成後に人間レビューを待つ | レビュー対象を蓄積し、短いポイントでまとめて判断を受け、開発へ戻す |
| 一つの素材で成立させる | 修正に使った素材と、別の未調整素材での結果を分けて確かめる |
| 後修正を実装する | 修正で得た知見を、次の自動出力にも適切に反映する |

**採用済み機能の再承認、黒接続の優劣研究、受理済みQCの再証明を、新計画の入口にはしない。**

## 2. 目指す状態

目標は引き続き、**「見たものが気持ちいい動画を作る」**こと。

これを演出数、無音秒数、平均字幕長、AIの総合点など一つの数値へ置き換えない。今後は、次の流れを実際に回せる状態を作る。

自動Digestを作る
→ 完成した映像・音声を観測する
→ 改善の可能性がある箇所を整理する
→ 人間に必要なポイントだけまとめて見せる
→ 判断を保存する
→ 該当する描画・選択・編集だけを修正する
→ 別のDigestでも改善が再現するか確かめる。

AIが指摘した箇所を、最初から「欠陥」とは呼ばない。技術故障、明確な内容不整合、好みの問題、複数が許容されるバリエーション、未確認の仮説を分ける。

## 3. 開発順序

旧工程I〜IVと混同しないよう、今後の品質改善工程はQ1〜Q5とする。

| 工程 | 作る・改善するもの | その工程で確認すること |
|---|---|---|
| **Q1：今回のレビューを実物へ反映** | Panelのセンタリング・画像背景、拡大縮小の滑らかさ | 指摘した問題が実際の短い動画で解消したか |
| **Q2：ポイントレビューを標準化** | 固定HTML＋レビュー用データ、回答と台帳の対応 | 毎回同じ操作で、正しい対象への判断を残せるか |
| **Q3：完成動画から改善候補を見つける** | AIによる観測と、根拠付きの確認ポイント抽出 | 計画だけでなく、実際の出力の問題を拾えるか |
| **Q4：自動使い分けを改善し、別Digestで確かめる** | 人間判断を反映した描画規則・意味判断・許容集合 | 同じ問題を減らしつつ、別の箇所を悪くしていないか |
| **Q5：素材選択・保持範囲・間・構成へ広げる** | Prospect選択、前後範囲、重複、接続テンポ等の改善 | 演出では解決できない編集上の問題を改善できるか |

**Q1とQ2は並行可能。Q3の観測経路の確認も、人間の再レビュー待ちと独立して進めてよい。** Q3・Q4は一回ずつ作って終了する工程ではなく、以後の品質改善の基本サイクルとする。

Q5の問題候補は早くから記録してよい。ただし、演出改善に紛れて本文や採用区間を変更せず、編集内容を変える作業として明確に分けて実施する。

## 4. Q1：進行中の修正を、そのまま仕上げる

現在進めている修正は中断・やり直しにしない。今回の人間レビューで明らかになった以下を最優先にする。機能自体への評価・修正要求を分離する。

### Panelの表示品質

背景に対する字幕のセンタリングを必須にする。設定上の座標が中央であることだけではなく、**実際に描かれた文字と背景が、整った配置として見えること**を確認する。短文・横長・複数行など、必要な違いを持つ少数の例で確かめる。

背景は色違いだけでなく、画像・テクスチャ・意匠の異なる有限のバリエーションを用意する。利用根拠のある素材を使い、出自と版を管理する。無断の外部取得や、AIが毎回自由な背景を生成する構成にはしない。

**「目立ちすぎないこと」は固定条件にしない。** 必要な場面では最も目立ってよい。修正するのは、整列の乱れや表示の作りの粗さであり、表現力そのものではない。

### 動きの滑らかさ

拡大縮小がカクカク見える原因を、実装側で特定する。動作を弱めることや削除することを、滑らかさの改善の代わりにしない。

補間、状態数、動作曲線、描画方法は、現行の許可範囲で適切に選ぶ。人間が特定のpresetを原因として名指ししたとは記録せず、実際にスケール変化を持つ箇所へ修正を割り当てる。

### Q1の完了条件

変更が実動画へ届き、必要な技術検査を通り、**センタリング・画像背景・拡大縮小の修正箇所だけを短く再確認できること**。

黒やSoftの採用を取り直さない。機能自体の採用と、修正後の出来栄えの確認を分ける。何周で終わるかは先に保証せず、残った具体的な問題だけを次へ回す。

## 5. Q2：標準ポイントレビューHTMLを作る

既存TODOの「人間レビュー用HTMLフォーマットの標準化」を、品質改善に必要な工程として繰り上げる。固定HTMLとレビュー用データを分離する方針は、そのまま採用する。

### 固定するもの

画面構造、ボタン位置、再生・停止・前後文脈の確認、必要な場合だけのBefore／After切替、回答方法を固定する。

各ポイントは、対象動画・対象区間・review_id・確認したい問い・回答の反映先を持つ。AIは毎回HTMLを設計せず、固定形式へ内容を入れる。

**一つの問いから、何を採用・修正できるのかが明確な単位にする。** 同じ区間にPanelとフェードが含まれていても、回答を両方へ自動配布しない。まとめた動きへの評価なら、まとめた評価として保存する。

### 人間への負担を固定しない

2〜3分の全編比較や、全字幕の採点を標準手順にしない。短いポイントを基本にし、判断に必要な場合だけ前後を広げられるようにする。

全体の流れを見たい場合は、必要なまとまりを参照できるようにするが、**全編視聴を品質合格の儀式にはしない。** 局所レビューしかしていなければ、全体品質を確認済みとは記録しない。

「良い」「直したい」「両方使える」「差が分からない」「今回は判断しない」を受け取れるようにする。理由や点数は必須にせず、原文を残してCodexが台帳へ整理する。

### Q2の完了条件

異なるレビュー用データを入れても同じ画面・操作で使え、回答が対象の動画版・ポイント・反映範囲へ正しく保存されること。

既存HTMLを土台に小さく実装し、汎用レビューサービスや新しい動画編集基盤にはしない。

## 6. Q3：完成動画を観測し、改善候補ポイントを出す

ここが、現在の修正が落ち着いた後の本命となる。

ただし、**「退屈を正しく判定する巨大な評価AI」を先に作らない。** 最初は、完成Digestから根拠付きの確認ポイントを作り、Q2の画面へ渡す小さな経路を成立させる。

### 観測するもの

既存の完成動画、字幕、表示時計、採用区間、保存済みの演出指定、利用可能な音声・映像観測を使う。

計画が指定どおりであることと、実際にどう見え、どう聞こえるかは別に確認する。例えば、計画上は中央でも実表示が不自然な場合や、有限状態の切替は正しくても動きが粗い場合を拾えるようにする。

| 分類 | 確認する可能性のある問題 |
|---|---|
| 表示 | センタリング、背景と文字のまとまり、動きの粗さ、必要な映像の覆い隠し |
| 演出配置 | 内容や反応と表現の不一致、必要な変化の不足、似た見せ方の連続 |
| 編集・文脈 | 前振り不足、重複、山の直前・直後の欠落、不要に続く部分 |
| 接続・音 | 切替時の発話や音の不連続、理解に必要な間、区切りの扱い |

これは検出すべき欠陥の固定リストではない。**同じ表現が続くこと、無音があること、目立つことを、それだけで悪いと判定しない。**

### 観測した事実と推測を分ける

各候補には、実際に観測した内容、推測している問題、判断に足りない情報、改善案または人間への問いを持たせる。

映像を見ていないなら、配置や見え方を観測済みとしない。音声を聞いていないなら、声の勢いや音の自然さを確認済みとしない。字幕・時間表から作った候補は、その範囲の推測と明記する。

**既存の許可された観測経路が使えるかを、Q3の最初に確認する。** Gemini等への過去の送信承認を、新しい素材や未確認の権利同意へ流用しない。使えない観測がある場合は不足として残し、利用できる観測と設計・データ接続を先に進める。

### 見落としと誤警報を減らす

演出が付いた箇所だけを候補にしない。通常表示の場面や接続前後も観測対象に含める。生成時の説明を正解として読み直すだけの自己評価にしない。

同じ問題の候補はまとめる。人間へ大量の「なんとなく気になる」を送らず、**確認することで何を決められるかが明確なものを提示する。**

「候補なし」は「全編品質合格」ではない。どこを何で観測したか、不足は何かを残す。

### Q3の完了条件

少数の実Digestについて、観測根拠と対象区間がある候補を作り、標準HTMLへ渡せること。

既知のセンタリングや動きの問題は、入力・出力の対応確認に使ってよい。ただし、既に答えを知っている例で見つけられたことだけを、新しい問題の発見能力の証明にはしない。

## 7. Q4：レビューを自動出力へ反映し、別Digestで確かめる

レビュー結果を単なるメモで終わらせず、次の生成へ戻す。ただし、**すべての感想を一般ルールに変えるわけではない。**

| 回答の種類 | 主な反映先 |
|---|---|
| センタリング・滑らかさ等の表示品質 | 描画部品・有限preset・その検査 |
| 特定の文脈で表現が合わない | 意味判断、根拠の使い方、許容表現の集合 |
| 一箇所だけ直したい | その動画のoverride |
| 複数の表現がどちらも使える | 許容候補として保持し、再現可能なバリエーション選択 |
| 判断できない・未観測 | 保留として保存。都合のよい正解ラベルにしない |

現在ある**「内容から許容集合を決め、その中で再現可能に選ぶ」**構造は維持する。新しいselectorをゼロから作らない。

人間レビューを「学習材料にする」とは、まず判断例・適用範囲・修正規則を保存して再利用することであり、モデルの追加学習やファインチューニングを必須にする意味ではない。

### 別Digestでの確認を後回しにしない

最初の対象は、現在調整中のDigestと、利用許可済みの別Digest一本を基本にする。

別Digestでは、修正前の出力を保存してから新しい規則を適用する。その素材の結果を見て調整した時点で、「未調整素材」の扱いを終える。

同じ字幕IDだけに効く特例を作らず、問題が再発しないか、別の箇所を悪くしていないかを見る。全編を何本も人間に比較させず、変更の影響箇所と新たな確認候補を標準HTMLへまとめる。

**Q3→ポイントレビュー→反映→別Digest確認**を、一つの改善単位として完了させる。改善が見られない場合も結果を残し、変更量を増やしたことを成果にしない。

## 8. Q5：演出では解けない問題を、編集内容へ戻す

次に広げるのは、ショートではなく、**ダイジェスト自身の編集品質**とする。

既存のProspect選択、前後範囲、保持、接続の仕組みを使い、必要な部分だけ改善する。

例えば、前振りが足りず反応の意味が伝わらない、同じ説明が重複する、見どころの後が長い、必要な一拍が切られている、といった候補を扱う。どれも、実際に問題があると決めつけず、観測とレビューで確認する。

**編集の問題を、派手な字幕や黒接続を足すだけで隠さない。** 逆に、見た目の問題しかないのに採用内容を変えない。

### 内容変更は、演出overrideと分ける

ここからは保持区間や本文・時刻が変わり得るため、確定済みDigestを上書きせず、**新しい編集案・新しい版**として保存する。

素材選択や保持範囲の変更は上流の編集処理で行い、rendererが勝手に本文や時刻を変える構成にはしない。内容が変わった場合、旧版の演出指定や人間overrideをID一致だけで無条件に移植しない。

最初は、既存素材から「前振り不足」か「不要な反復」など、具体的な一種類の問題を選んで通す。候補選択・切出し・並べ替え・音声処理を一度に作り直さない。

## 9. 後修正UI・性能・正式化は、並行の残件として管理する

工程IVのAおよびB/Cは技術受理済みで、実UI受入と性能課題は別に残っている。この状態は維持する。

**実UI受入**は、正式に許可された検証経路が成立した時点で再開する。完成したとは偽らないが、その環境待ちで表示品質の修正やポイントレビューまで止めない。

**性能改善**は、品質改善の反復や実操作を具体的に妨げる処理に絞る。初回周辺確認や適用検査の時間は残件として保持し、受理済みQCを毎回深掘りすることを主工程にはしない。

**正式trust・Normal基準・通常入口・release**は必要な段階でまとめて扱う。表現の使用許可と、正式な実行基準の認定を混同しない。同時に、正式化だけを理由に品質改善を延々と止めない。

## 10. 全工程に共通する運用

### 人間レビューは蓄積してよい

本人の常時待機を前提にしない。技術作業は独立範囲で進め、判断が必要なものをHuman Review Pendingへ蓄積する。

回答を受けたら、**原文・対象版・判断・適用範囲・修正状況・反映確認**を分けて保存する。「回答済み」「採用済み」「修正済み」「確認済み」を一つの完了表示に潰さない。

短いポイントでまとめて確認し、無回答を承認へ変えない。比較不能な微差には、唯一の正解を要求しない。

### 技術検査は品質改善を支える

意図して変えた画素・動き・編集内容と、守るべき本文・時計・来歴を分ける。変更箇所は小型で直接検査し、全編は必要な節目で確認する。

受理済みの証拠は、入力と版が合う範囲で再利用する。検査数、生成動画数、commit数を品質向上の代用にしない。

### 作業の広がりを抑える

新しい巨大な評価基盤、汎用NLE、自由な編集Agent、大量の新演出、根拠のない品質スコアや重み付きランキングを先行開発しない。

AIの観測結果だけで人間の好みや正式採用を決めない。一方、人間には不要な全件再検査や理由説明を求めない。

新規費用、外部素材送信、権利確認、新依存、正式契約変更等の境界は維持する。境界に当たった部分だけを切り分け、独立作業まで停止しない。

生成データは管理済みの保存先へ置き、必要なsource・test・軽量記録を選別してcommit／pushする。未管理データの再流入を防ぐが、そのために毎回全workspaceを棚卸ししない。

## 11. 新計画で最初に進めるまとまり

**進行中のPanel・動きの修正を仕上げ、その再レビューを固定HTML形式に載せる。これを最初のまとまりにする。**

新しいHTMLを毎回作る流れをここで終え、今回の修正箇所と次のレビュー項目を同じ形式で扱えるようにする。標準化が間に合わないことだけを理由に、既に見られる修正版の提示を遅らせない。

その間に、Q3の観測経路と既存データの再利用可能性を確認する。次の主な実装単位は、**完成Digestから、根拠付きの品質改善候補を抽出し、標準ポイントレビューへ渡す最小経路**とする。

その後は、候補を出して終わらず、**レビュー反映と別Digestでの確認まで**進める。

今回の計画変更は、「ダイジェストが一通りできたから次の製品へ」ではない。できたダイジェストを材料にして、ZEV自身の出力を良くする段階へ進む変更である。

現在の修正を続けながら、**Q1・Q2 → Q3・Q4の改善サイクル → 必要な編集品質のQ5**を本線にする。ショートへの移行は、別途kawafmmが許可するまで行わない。
