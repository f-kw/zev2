# ZEV 遠方接続 設計資料

**v0.2 — 「見たものが気持ちいい」を主目的とする設計**

## 1. 目的

ZEVが作るものの主目的は、次の一点とする。

> **見たものが気持ちいい動画を作る。**

遠方接続は、その気持ちよさを増やす場合にだけ使う補助手段である。遠方接続自体を作ることは目的にしない。

この目的から、次を明示的に認める。

- 遠方接続がない配信からもショート動画を作る。
- 遠方接続が見つからないことは欠陥ではない。
- 意味上の関係が正しいだけの接続は採用しない。
- 後半の体験が良くならないなら、前半は付けない。

## 2. 旧設計からの変更

旧設計の主線は、配信全文から意味的に関連する遠方の前半と後半を先に探し、動画化した後で良さを確認するものだった。

v0.2では、この順序を主線から外す。

**旧い主線**

意味的な遠方接続を探す → 映像にする → 良いか確認する

**新しい主線**

単独でも気持ちいい終点を人間が見つける → 終点を固定する → 必要なときだけ過去の前半を逆引きする → 後半単独と前半追加版を人間が見比べる

## 3. 遠方接続の2種類

### 3.1 腑に落ちる型

後半の場面自体が、すでに見る価値を持つ。過去の場面を先に見せることで、次のように後半の体験が増すものを扱う。

- なぜそうなったかが分かる。
- 過去の予告や宣言が回収されたと分かる。
- 過去の判断の結果だと分かる。
- 以前の認識や期待が覆ったと分かる。

探索順序は次で固定する。

1. 単独でも気持ちいい後半を、人間が実動画で見つける。
2. 人間が後半の素材と区間を固定する。
3. Lunaは固定された後半の価値を増やす過去の前半だけを全文から逆引きする。
4. 同じ後半を使った「後半だけ」と「前半 → 後半」を人間が見比べる。
5. 前半によって後半の気持ちよさが増した場合だけ採用する。

Lunaは後半を自由に選ばない。候補の採否も所有しない。

### 3.2 カタルシス型

個々の場面ではなく、次の線全体を見たときに気持ちよさが生まれるものを扱う。

**課題 → 失敗・悪化 → 転換またはさらに大きな失敗 → 解決**

- 最大4場面を基本とする。
- 3場面で成立する場合は3場面で終える。
- 5場面以上にはまだ広げない。
- 途中の場面は説明ではなく、失敗、悪化、方針変更、突破口など、状態が変わった瞬間を優先する。
- 途中で一度完全に解決し、その後に同じ問題が再発した場合は、再発以降だけを1本の線とする。

探索は解決側から逆向きに行う。

1. 解決らしい場面を見つける。
2. その結果の前に何に困っていたかを追う。
3. その困り事が最初に明確になった場面を追う。
4. 必要な場合だけ、途中の状態変化を追加する。

この型は2場面の遠方接続とは別の仕事である。まず少なくとも3本の人間確認済み正例を集め、その後に入力・出力・確認動画の形を設計する。現段階でAI探索器は作らない。

## 4. 人間観測の方針

「良い」の詳細定義を先に固定しない。

最初の一周で候補ごとに記録するのは次の3値だけとする。

- 良い
- 良くない
- 分からない

最初の一周で理由を必須にしない。接続成立、回収強度、映像適性、接続型、詳細な不採用理由も要求しない。Gemini等に先行採点させない。

「良い」と感じた候補だけを後で再確認し、時間を置いて二度見ても良いものを強い正例とする。詳細な品質分解は粗い選別を通過した候補にだけ行う。

## 5. 腑に落ちる型の後半候補

後半候補はLunaではなく、実動画を見た人間が選ぶ。最初は次の2経路を調べる。

### 5.1 コメントが増えた98区間

`o8rZAhARXAc`では、配信平均よりコメント数が多い完全な1分区間が98件ある。これらは遠方接続候補ではなく、単独でも見たい後半候補を人間が見つけるための索引として使う。

既存の元動画の部分配信と開始・終了時刻での自動停止は再利用できる。そのため98本の動画を書き出す必要はない。

最小の確認方法は、元動画1本を使い、98区間を時系列で順に開くローカル確認ページである。連続する区間は39グループの見出しにまとめられるが、98個の正式区間は結合・選別しない。全部を等速で見た場合の映像尺は98分である。

現時点で、この98区間に専用する正式な確認結果の器はない。ローカルで一時的に見るだけなら新しい動画契約は不要だが、確認順と人間の観測を正式に保存する場合は、最小のforward-only確認契約が必要になる。

### 5.2 通常切り抜き経路

現行の通常候補探索は、おおむね次の順で進む。

コメント流量で文字起こしの対象を選ぶ → 文字起こしからGeminiがテーマ候補を作る → Geminiが候補を並べる → 人間が実動画を見て公開価値と境界を選ぶ

候補作成と順位付けは文字起こしと説明に依存し、実映像を直接評価するのは後段の人間確認である。そのため、この経路は「気持ちいい後半」の原料候補を供給できる可能性があるが、AI出力だけで後半を確定はできない。

既存の人間確認履歴には、「公開したい」と判断された通常候補と人間が選んだ区間が存在する。ただし、これらは個別実験の結果であり、任意の通常候補を「腑に落ちる型の固定後半」として動画・候補・人間承認のSHAまで一般的に束縛する入口は現時点で確認できない。正式な受け渡しを行う場合は新しいforward-only入口の承認が必要である。

## 6. `o8rZAhARXAc` 7候補の一次確認

旧設計で得た7候補と候補確認動画14本は削除せず、新設計に偶然役立つ実例が含まれるかを1回だけ見る。

ただし、既存の評価契約は3段階の文章記録と詳細な品質評価を必須にしており、「分からない」も持たない。新しい一次確認の3値を意味変更なしに保存できない。既存の詳細契約に押し込まず、理由欄を持たない最小の3値一次確認契約が必要である。

この一次確認の「良い」は、正式selection、最終採用、強い正例のいずれも意味しない。

## 7. カタルシス型の現在地

既存の通常候補と人間評価を読み直すと、単独で良いと判断された候補は存在する。例えば `o8rZAhARXAc` の「劇的勝利に大絶叫し涙を流す」場面は、人間が「公開する」と判断した終点候補である。

しかし、既存成果物には、その終点へ至る課題、失敗・悪化、転換を同じ線として人間が確認した記録がない。他の候補にも部分的な流れはあるが、カタルシス型の3〜4場面の正例として確定できない。

したがって、今回確認した正式成果物内では、3〜4場面の線として人間確認済みの正例は0本である。3本以上が集まるまでAI探索器を実装しない。実例の正式保存に新しい契約が必要となった地点でconsultationへ戻る。

## 9. 責務の分離

| 段階 | 担当すること | 担当しないこと |
| --- | --- | --- |
| 通常候補・コメント区間 | 実動画で見る後半候補の索引を出す | 遠方接続の採否を決める |
| 人間 | 単独で見る価値のある後半を選び、区間を固定する | 選択をAIの採点に委ねる |
| Luna | 固定済みの後半を増幅する過去の前半を意味探索する | 後半の選択、映像価値の確定、最終採否 |
| 決定論的コード | 候補・発話・区間・動画のIDとSHAを解決・検査する | 未知IDの推測、候補の意味補正 |
| 動画生成・技術検査 | 承認済み区間を再現可能に描画し、映像・音声・時間対応を検査する | 作品の良さや採否を決める |

## 10. 安全運用

- 有料AIは実行前に回数と費用上限を明示し、kawafmmの承認を受ける。
- 自動再試行は行わず、失敗時は証拠を保存して停止する。
- 人間が最終採否を所有する。
- 映像の価値は実動画を見て判断する。
- 既存の正式成果物を削除・上書きしない。
- forward-onlyを維持する。
- 無関係な変更をcommitへ混ぜない。
- push・remote操作は行わない。

## 11. 現在の停止点と次の最小単位

現在は、次の新しい正式契約の要否が判明した地点である。必要と確認できた契約は承認前に実装しない。

1. `o8rZAhARXAc` 7候補を「良い / 良くない / 分からない」だけで一周する、理由非必須の一次確認契約。
2. 98の正式コメント増加区間を元動画で順番に見るだけなら新契約は不要である。確認済み状態と粗い人間観測を正式保存する場合に限り、最小確認契約が必要になる。
3. 実動画を見て人間が選んだ通常候補を、腑に落ちる型の固定後半として候補・区間・元動画・人間承認のSHAで束縛する受け渡し契約。

最初の実装候補は1の最小3値確認である。既存の14本の確認動画をそのまま使えるため、新しい動画生成やAI通信を要しない。

98区間の確認は、新しい動画byteを作らず、元動画の部分配信とseekによる薄いページとする。通常候補の受け渡しは、既存の人間結果を置き換えず、forward-onlyの束縛入口とする。

カタルシス型は実例の人間観測を先に行う。保存契約が必要となったときは、実装前にconsultationへ戻る。

## 13. 候補発見後の共通Gemini動画理解（2026-09-03追補）

遠方接続候補だけに専用のGemini工程は作らない。通常候補、コメント起点候補、遠方接続候補、将来のカタルシス候補など、異なる経路が発見した候補を、候補発見後の共通動画理解へ渡せる構造を目標とする。

共通工程へ渡す前に、ZEVの決定的処理が粗い候補動画、元動画への時刻写像、正式発話との束縛、媒体SHAを用意する。Geminiは実映像・音声・発話から、核となる出来事、原因、最小限の導入、反応、自然な終端、外せる前後、映像上の注意、判断材料不足を観測する。

Geminiの回答時刻は正式区間ではない。ZEVが候補動画内の時刻を検査し、元動画時刻へ投影し、正式発話との包含・重なりとSHAを確認した後、人間が区間と採否を決める。発話IDから時刻への変換、base-media、frame mapping、字幕閉包、presentation instruction、renderer admission、renderer、技術QC、最終人間確認は既存責務として残す。

3時間18分の配信全体を対象にしたAgentic動画理解実験は削除しない。Agentic処理が正常に起動し短い候補を返した一方、長尺全域を漏れなく探索したことは証明できなかった。この実験は、長尺全域探索をGeminiの主用途にしないと判断した観測履歴として保持する。

最初の比較では、既存の人間評価済み候補5本を使い、人間評価をGeminiへ見せず、映像事実と役割区間だけをstructured outputで受け取る。点数、合否、順位、最終採否は返させない。既存4本には人間が選んだ境界が動画端として暗黙に含まれるため、内容観測の比較には使うが、広い粗抽出から境界を発見できたという独立証拠にはしない。

共通工程、5本の現物検査、API方式、費用算定、job/result案、既存通常Gemini経路との関係は `docs/ZEV_候補動画理解_設計資料_v0.1.md` を正本とする。この追補は過去の遠方接続設計と実験履歴を置き換えず、以後の責務分離だけをforward-onlyで追加する。

この追補以後、11節の「最初の実装候補」は当時の停止点として履歴保持し、現在の最初の実装案は共通 `candidate-video-understanding` job/result契約と決定的検査である。どちらも新しいkawafmm承認前には着工しない。
