# ZEV 遠方接続 設計資料

**v0.1 --- 「理解を増やす接続」とその探索ロジック**

## 1. 目的

遠方接続は、配信内で時間的に離れた区間を接続し、後半区間の意味・背景・経緯を視聴者がより深く理解できる動画を作る機能とする。

基本定義は次のとおり。

> **遠方接続 = 後半の意味を増やす前半を探し、先に接続すること。**

単に時間的に離れた関連シーンをつなぐのではなく、前半によって後半の人物の意図、行動の理由、状況の背景、過去の経緯、発言の指示対象、反応の理由、目標、期待と結果の関係などがより分かることを狙う。

## 2. 第一版では「面白さ」を直接判定しない

第一版では「面白いか」を独立した評価軸として扱わない。

判定対象は、

> **前半を付けることで後半をより理解できるか**

とする。

理解が増えた結果として後半がより面白くなることは期待するが、LLMには編集センスや笑いそのものの判定を主目的として要求しない。

これにより、遠方接続を長文読解、照応、因果関係、目的、背景関係の探索問題として扱える。

## 3. 採用判定の核

遠方接続候補の中心判定は次の問いとする。

> **前半を見ずに後半だけを見た視聴者と、前半を見てから後半を見た視聴者で、後半の出来事に対する理解に明確な差が生じるか？**

単なる関連性では不足する。

さらに、追加される理解は後半の中心的な出来事・発言・反応に関係している必要がある。

LLMは候補ごとに、

> **前半を追加すると、後半について何が新しく分かるのか**

を具体的に説明する。

この説明が具体化できない候補は原則として落とす。

## 4. 例

### 採用しない例

-   前半：「今日はマイクラをやります」
-   後半：マイクラで家を建てている

関連はあるが、前半を付けても後半の理解はほとんど増えない。

### 採用候補の例

-   前半：「今日は絶対ダイヤを見つけて帰る。見つかるまで終われない」
-   後半：数時間後、ダイヤを発見して大きく反応する

追加される理解は、「本人が長時間この達成を目標にしていた」「なぜ発見時の反応が大きいのか」である。

## 5. 遠方接続の2パターン

### 5.1 深化型

すでに動画候補として成立する後半を起点にする。

**後半 → 過去探索 → 前提追加**

後半だけでも成立するが、過去の発言や出来事を先に見せることで、その意味、理由、背景、反応などを深く理解できるようにする。

### 5.2 成立型

前半に存在する未完了要素を起点にする。

**課題・目標・疑問・予告など → 未来探索 → 結末追加**

たとえば以下を対象にできる。

-   目標 → 達成 / 断念
-   課題 → 解決 / 未解決
-   疑問 → 判明
-   予告 → 実行 / 不実行
-   予想 → 結果
-   懸念 → 現実化 / 杞憂
-   挑戦 → 成功 / 失敗
-   計画 → 実行 / 変更

成立型では「単体では弱い後半」を直接探す必要はない。前半で生じた open
loop を見つけ、その後にそれを閉じる resolution を探索する。

## 6. 後半を基準点にした探索

深化型では、全文から前半・後半のペアを同時に探索するのではなく、まず後半を基準点として確定させる。

基本形は、

1.  後半候補を抽出する
2.  その後半について過去を探索する
3.  接続候補を生成する

とする。

LLMへの問いは、

> **この後半をより理解するために有用な情報が、それ以前のどこにあるか？**

という形にする。

これにより、探索空間と役割を明確にする。

## 7. LLMと人間の役割

ZEVではLLMに「一番面白いもの」を決定させない。

基本方針は、

-   **LLM = 候補探索器**
-   **人間 = 編集価値の最終判定者**

とする。

LLMには意味的に成立する候補を複数出させ、人間がその中から採用するものを選ぶ。

したがって、LLM側では精密な面白さランキングよりも、良い候補を取りこぼさないことを重視する。ただし人間の確認負荷を抑えるため、明らかに成立しない候補は除外する。

## 8. 現行ZEVとの関係

現行の素材区間化処理自体は、面白さを理解して区間を選んでいるわけではない。

基本的には、

**テーマ → 関連発話ID → 発話ブロック → タイムスタンプ → 動画区間**

という決定論的な変換を行う。

過去にはGeminiが文字起こしから、

-   テーマ
-   代表発話
-   関連発話ID
-   切り抜きになる理由
-   構成方針

を生成する経路が存在し、LLMが意味を読んで候補探索を行っていた。

遠方接続も、この既存思想を拡張する。

Lunaが意味的な遠方接続候補を探索し、前半・後半の発話IDを生成した後、既存の区間化・出力処理へ渡す構造を基本とする。

探索と動画区間化は疎結合のまま維持する。

## 9. 既存実験から得られている知見

過去のテーマ生成実験では、人間作成の正解テーマや正解区間をfew-shotとしてLLMへ渡していたわけではない。

一方で、次の人間知見は間接的に利用されていた。

-   チャット流速上位100分をLLM入力範囲として利用
-   VTuber本人の言動・感情・関係性を重視するランキング原則

チャット流速上位100分を入力したテーマ生成では、人間採用13区間中12件を拾った実績がある。

この結果から、正解例そのものを学習させるよりも、

**人間が探索問題の形を良くする → LLMが候補を広く探索する → 人間が選ぶ**

という構造が有効だったと考える。

## 10. コメント流量を使った遠方接続探索

遠方接続では、コメント流量が増加した区間を、

> **「遠方接続の片割れである可能性が高い場所」**

として利用する。

コメント増加区間そのものを「面白い場所」と断定する必要はない。

その区間をアンカーとしてLunaが意味を理解し、時間的に離れた相方を探索する。

### アンカーが後半の場合

**コメント増加区間 → 過去探索 → 前提発見**

その場面の中心的な出来事・発言・反応を理解するために有用な過去の情報を探す。

これは主に深化型へつながる。

### アンカーが前半の場合

**コメント増加区間 → 未来探索 → 結末・回収発見**

その場面で発生した課題、目標、疑問、問題、予告などについて、その後に起きた解決、結果、変化、断念などを探す。

これは主に成立型へつながる。

### コメント流量の役割

コメント流量で前半と後半の両方を絞り込む必要はない。

重要なのは、

> **片側だけ発見できれば、そこを索引として意味探索を開始できる**

こと。

たとえば前振りは静かでも回収時にコメントが急増する場合、回収側をアンカーにして過去の前振りを発見できる。

逆に、問題発生時だけコメントが急増し、解決時にはコメントが静かな場合でも、問題発生側をアンカーにして未来の解決を発見できる。

したがってコメント流量は「両端を選別するフィルター」ではなく、**遠方接続探索を開始するための片側アンカー候補抽出器**として扱う。

## 11. 現時点の探索フロー

現時点での基本フローは次のとおり。

**コメント流量** → **アンカー候補抽出** → **Lunaがアンカーの意味を理解**
→ **過去または未来へ相方を意味探索** → **遠方接続候補を複数生成** →
**人間が採否** → **発話IDを既存の区間化・出力処理へ渡す**

全発話同士の総当たりを避け、反応の強い区間を起点に意味探索することで探索空間を縮小する。

## 12. 今後、実データを見て決める事項

-   コメント増加区間をどのように抽出するか
-   アンカーごとに過去・未来の両方向を常に探索するか
-   Lunaへ渡す文字起こし範囲
-   open loop の表現形式
-   前半・後半それぞれの区間長
-   1つのアンカーに複数の相方を許すか
-   候補数と除外閾値
-   発話時刻から動画切り出し範囲への補正
-   人間の採否結果を将来どう利用するか

## 13. 初期実装で採用する探索単位

初期実装では、コメント流量から得たアンカーを1件ずつ別々にLunaへ処理させるのではなく、**配信全文と複数のアンカー候補をまとめてLunaへ渡し、一括して遠方接続候補を探索させる方式を第一候補とする。**

理由は次のとおり。

-   遠方接続そのものが長距離の文脈を扱う処理であり、配信全体を俯瞰できることに価値がある
-   アンカーごとに同じ全文を繰り返し処理する無駄を避けられる
-   複数アンカー間の関係も含めて判断できる
-   Lunaに「配信全体の中で、このアンカーと意味的につながる離れた区間」を探させるという役割が明確になる

したがって初期形は、

**配信全文STT + コメント流量アンカー群 → Lunaによる一括探索**

とする。

ただし、実走でコンテキスト量、精度、コスト等に問題が出た場合は、アンカー単位またはアンカー群単位への分割を検討する。

## 14. アンカーの前半・後半分類を事前に固定しない

深化型と成立型は完成した接続の性質を説明する分類として維持するが、**探索開始前にアンカーを「前半」「後半」のどちらかへ分類する処理は必須としない。**

各アンカーについてLunaに、時間的に離れた区間に次のどちらかが存在するかを探索させる。

1.  **過去側の前提**\
    アンカーの中心的な出来事・発言・反応を理解するために有用な過去の情報。

2.  **未来側の回収**\
    アンカーで生じた課題、目標、疑問、予告、問題、期待などを解決・完結・変化させる後の出来事。

つまり、探索時には原則として**前後双方向を候補にする**。

その結果、

-   過去側に有効な相方が見つかった接続は主に「深化型」
-   未来側に有効な相方が見つかった接続は主に「成立型」

として整理できる。

これにより、深化型と成立型のために別々の探索アルゴリズムを用意する必要を減らし、共通の意味探索として実装できる。

## 15. 実装前の基本形

以上をまとめると、初期実装の基本形は次のとおり。

**配信全文STT + コメント流量情報** → **アンカー候補群を抽出** →
**全文とアンカー群をLunaへ一括入力** →
**各アンカーについて過去・未来の両方向から意味的な相方を探索** →
**前半発話ID・後半発話ID・追加される理解を持つ遠方接続候補を複数出力** →
**人間が採否** → **採用候補を既存の区間化・出力処理へ渡す**

この段階では、コメント流量の具体的閾値、アンカー数、遠方とみなす時間差、表示候補数などの数値は固定しない。最初の実走結果を見て決定する。
## 16. Codex実装レビューの結論

現行ZEV2実装との比較レビュー結果は、

> **B. 小さな設計修正後に進める**

とする。

遠方接続の中心設計そのものは維持する。

- 意味探索と区間化・描画を分離する
- Lunaは時間的に離れた意味関係を探索する
- LLMは候補探索、人間は編集価値の最終判定を行う
- 採用後に既存の区間化・描画資産へ接続する

再設計は不要であり、修正対象は主に**データ契約と既存ZEVへの接続方法**である。

## 17. 遠方接続を置く位置

遠方接続探索は、既存テーマ選択の後だけに置かない。

成立型では、前半の課題・目標・疑問・予告などから新しい候補そのものを発見する必要があるため、既存テーマ生成と並ぶ候補生成処理として扱う。

初期の概念フローは次のとおり。

**STT**
→ **正式な意味発話単位への整形**
→ **コメント流量からアンカー候補生成**
→ **遠方接続探索**
→ **人間が候補を採否**
→ **採用候補の最終区間決定**
→ **composition**
→ **演出・描画**

既存テーマ候補と遠方接続候補は、同じ候補生成層に存在し得る。

## 18. 正式な意味発話ID層

実STTには、1文字1segmentのような細かすぎる成果物が存在するため、LLMが直接参照する正本IDとしては扱わない。

遠方接続では、LLMが意味として読める単位へ結合した**正式な意味発話ID**を定義する。

この意味発話には最低限、次を保持する。

- 正式な意味発話ID
- 発話本文
- 開始時刻
- 終了時刻
- 元STT segment IDとの対応
- 参照している文字起こしの版・SHA等のbinding

Lunaはこの正式発話IDを入力・出力に使用する。

時刻そのものをLLMに生成させず、採用された発話IDからローカル処理で決定的に復元する。

## 19. 遠方接続専用成果物

遠方接続の探索結果を、既存の平坦な `関連発話ID[]` に直接変換しない。

平坦化すると、

- どのID群が前半か
- どのID群が後半か
- 前半と後半の組関係
- 何が新しく分かるのか
- どの文字起こしを参照した結果か

が失われるため、遠方接続専用の版付き成果物を持つ。

最低限、次を保持する。

- 候補ID
- 元動画ID
- transcript binding（版・SHA・ID体系）
- 順序付き前半発話ID群
- 順序付き後半発話ID群
- アンカー情報
- 前半によって追加される理解、または前半から後半で回収される内容
- 人間の採否結果

深化型・成立型の種別は保持してもよいが、探索前の必須分類にはしない。

## 20. 発話IDと最終動画区間を分離する

Lunaが返す前半・後半発話IDは、**意味上の根拠**であり、完成動画の切り出し境界ではない。

採用後に別工程で、

- 必要な導入文脈
- 発言の始まり
- 反応の収束
- 会話として自然な終端

を含めた最終素材区間を決める。

したがって処理は、

**意味探索**
→ **人間採用**
→ **最終区間決定**
→ **composition / render**

とする。

既存の区間選択資産は再利用候補とするが、遠方接続成果物をその入力へ変換する正式な接続処理を設ける。

## 21. コメント流量から正式アンカーIDへの変換

既存のコメント流量処理は1分単位の時刻範囲を生成できる。

遠方接続では、その時刻範囲をそのままLunaのアンカー識別子にせず、**正式な意味発話IDへ決定的に変換する処理**を置く。

概念的には、

**コメント流量上位の時刻範囲**
→ **その範囲と交差する意味発話を特定**
→ **正式アンカー発話ID群を生成**

とする。

具体的なコメント流量閾値や上位件数は実走後に決めてよいが、時刻範囲から正式発話IDへ結ぶ規則は実装前に固定する。

## 22. Luna実行境界

「全文STT + 複数アンカーをLunaへ一括入力」を第一候補として維持するが、現時点ではZEV2内で正式な受理実績がない。

そのため、正式生成の前に以下を行う。

1. 正式な意味発話形式で全文入力を生成する
2. コメント流量アンカー群を追加する
3. structured output schemaを追加する
4. プロンプト・出力予約を含めたtoken量を正式計測する
5. 容量・費用・失敗条件を確認する
6. 問題なければ全文一括方式で実走する

全文一括が不適合だった場合にのみ、アンカー単位またはアンカー群単位への分割を検討する。

したがって、**全文一括を仮定して実装を進めるのではなく、正式token計測を着工条件に含める。**

## 23. 既存資産の再利用方針

再利用候補は次のとおり。

- 過去のGeminiテーマ生成
  - 文字起こしから意味候補を作る思想
  - 代表発話ID・関連発話IDを返す構造

- callback探索
  - 後半基点から過去を意味探索する処理
  - IDを返し、時刻をローカル復元する方式
  - 文字単位STTを読みやすい発話へ結合する処理

- コメント流量集計
  - 1分単位集計
  - 配信内平均との比較
  - 相対値ランキング

- composition系
  - 離れた複数場面の最終境界決定
  - 複数区間の素材化

- edit plan / renderer
  - 複数区間の時系列連結
  - 音声を含む描画
  - 元発話時刻から完成動画時刻への写像

ただし、過去のcallback探索は探索技術の再利用材料であり、探索品質そのものが実証済みとは扱わない。

過去の人間確認では「関連はあるが原因・前提ではない」候補が出ているため、今回定義した、

> **前半によって後半の何が新しく分かるのかを具体的に説明できること**

を品質条件として使う。

## 24. 実装前に固定する4課題

Codexレビューで挙がった必須事項を、実装前仕様として次の4課題に整理する。

### 24.1 意味発話層

LLMが読み、返す正式発話単位とID体系を定義し、元STTとの対応を正本化する。

### 24.2 遠方接続成果物

前半・後半を組として保持し、追加される理解、アンカー、transcript binding、人間採否を保持できる専用成果物を定義する。

### 24.3 アンカー変換

コメント流量の時刻範囲を、正式な意味発話IDへ決定的に変換する。

### 24.4 Luna実行境界

正式入力でtoken計測を行い、全文＋複数アンカー一括方式が成立するか確認する。

この4課題が決まれば、遠方接続の意味設計としては実装へ進める状態とする。

## 25. 初回実走後に決める事項

次の数値・運用条件は着工前に固定しない。

- コメント流量の閾値
- アンカー数
- 「遠方」とみなす時間差
- 表示候補数
- 1アンカーに複数相手を許すか
- 前後素材区間の標準長
- 常に前後両方向を見るか
- 人間採否結果の将来利用方法
- 全文一括が不適合だった場合の分割単位

これらは初回実走で候補品質、確認負荷、token量、費用、処理時間を確認してから決める。
