# ZEV Human Review Accumulation Policy v001

作成日: 2026-09-20
状態: 正本運用ポリシー
適用範囲: ZEVの動画生成・演出・接続・自動配置・後修正・UIに関する人間レビュー全般

## 1. 目的

ZEVでは、人間が常時開発へ張り付くことを前提にしない。

技術検証と人間レビューを分離し、人間判断が必要な事項を失わず蓄積し、適切なタイミングでまとめてレビューし、その結果を対象範囲へ正しく反映する。

「すぐレビューしないこと」は失敗ではない。
失敗とは、レビュー待ちを記録せず失うこと、別の成果物へ誤適用すること、未レビューを採用済みとして扱うこと、レビュー結果を必要以上に一般化することである。

## 2. Human Review Pending を正式な開発状態とする

技術的に成立したが、人間の見心地・自然さ・使いやすさ・正式採用判断が残るものは、必ず `HUMAN_REVIEW_PENDING` として登録する。

`HUMAN_REVIEW_PENDING` は未実装・失敗を意味しない。

以下を必ず分ける。

- 技術成立
- 技術監査受理
- Human Review Pending
- Human Review 済み
- 正式採用
- 保留
- 不採用

人間レビュー未実施の機能を、技術試験の成功だけで正式採用へ昇格させない。

## 3. Pending項目に必ず保存する情報

各Pending項目は少なくとも次を持つ。

- review_id
- 対象機能 / 表現 / UI / 自動判断
- 人間に確認したい問い
- 現在の技術状態
- 対象成果物
  - 動画SHA-256
  - 対象動画の所在
  - plan / judgment / rules / renderer 等の関連versionまたは識別子
- 何を見れば判断できるか
- 判断結果によって変更する可能性がある範囲
- 判断結果によって変更してはいけない範囲
- 他のPendingとのbatch候補
- status
- 作成日 / 更新日

対象成果物へ束縛できないレビュー項目を「後で見る」の一言だけで残してはいけない。

## 4. レビューはまとめてよい。原則としてまとめる

人間レビューを機能ごと・commitごとに即時実施する必要はない。

むしろ、完成動画として同時に評価した方が自然な項目は、`Human Review Batch` へまとめる。

原則:

- 個々の演出を細かいA/Bで大量採点しない
- 実際に使われる完成動画・まとまった候補を優先する
- 同じ視聴で判断できるPendingは一つのBatchへ束ねる
- 人間の拘束時間を増やすためだけの比較動画を作らない
- 技術上独立して進められる作業は、レビュー待ちを理由に停止しない

ただし、人間判断が次の実装の意味を決める場合だけ、その依存部分を停止する。

## 4.1 人間の集中力を前提にレビューを設計する

2〜3分級の動画を最初から最後まで集中して見せ、細かな差分・演出採否・前後比較を人間に要求することを標準手順にしない。

長い連続視聴では、人間の注意・短期記憶・比較精度が落ち、AIが保持している時刻・状態・差分よりもレビュー品質が低下し得る。これは人間側の失敗ではなく、レビュー設計上の品質リスクとして扱う。

原則:

- AIが保持できる時刻・状態・差分はAI側で整理し、人間には判断が必要な短いポイントだけを提示する。
- 細かな差分、演出採否、Before/Afterは Point Review を使う。
- Whole Video Review は、全体のテンポ・単調さ・一本としての見心地など、本当に全体でしか判断できない項目に限定する。
- 「全部見せる方が安全」という理由だけで全編比較を要求しない。
- 人間に長時間の集中を要求するほどレビュー品質が上がるとは仮定しない。
- 複数の異なる機能を一つのポイントへ束ねる場合は、回答を各機能へ自動分配しない。機能別に帰属できる問いへ分けるか、bundle-levelの判断として保存する。
- 比較不能な微差や役割違いについて、無理に優劣を決めさせない。「両方使える」「なんとなくの違い」「人間にはほぼ比較不能」という判断も有効な製品判断として保存する。

## 5. Batch Review の作り方

Batchを人間へ渡す前に、Codex/Agentは次を準備する。

- review_batch_id
- 対象動画を1本または必要最小限の本数へまとめる
- Batchに含まれるreview_id一覧
- 各review_idが動画のどこで確認できるか
- 何を判断してほしいかを短く書く
- 技術的に成立済みの事項と、人間が決める事項を分ける
- 以前の人間判断がある場合は、その適用範囲を明記する

人間には「全部細かく採点してください」ではなく、完成物を見て必要な判断だけ返せる形にする。

## 6. 人間レビュー結果の記録

人間の回答は感想だけで保存せず、必ず構造化して記録する。

最低限:

- review_id
- reviewed_artifact_sha256
- decision
  - ADOPT
  - ADOPT_WITH_CHANGE
  - REJECT
  - DEFER
  - NO_DECISION
- 人間の原意を損なわない短い理由
- 適用範囲
- 非適用範囲
- 必要な変更
- 再レビュー要否

例:

「Shakeが嫌い」
と一般化しない。

対象Digestの特定の反応字幕に対して強すぎる、という判断なら、
その対象・文脈・自動選択条件への反映として記録する。
Shake自体の全面禁止へ勝手に拡張しない。

## 7. 反映規則

人間レビュー結果は、対象となった成果物・version・判断範囲へだけ反映する。

禁止:

- 古い動画への判断を新renderer版へ無言で移す
- 一例への不満をpreset全面廃止へ拡張する
- 「問題なし」を全用途の正式trustへ拡張する
- 未レビューの別表現を同時に採用扱いへする

新しい版へ判断を引き継ぐ場合は、
「何が同一で、何が変わっていないため移せるのか」を記録する。

## 8. レビュー結果を開発へ戻す手順

基本サイクル:

技術成立
→ HUMAN_REVIEW_PENDING 登録
→ 技術開発は独立範囲で継続
→ Human Review Batch 作成
→ 人間レビュー
→ 結果をPending台帳へ保存
→ 影響するpreset / selector / orchestration / UIだけ修正
→ 必要なら候補を再生成
→ 再レビューまたはCLOSED

レビュー結果を受けて関係のないarchitectureや機能まで作り直さない。

## 9. Codex / Agent の自走ルール

Codex/Agentは人間レビュー待ちが存在しても、独立して安全に進められる技術作業を止めない。

一方で、以下は勝手に決めない。

- 人間の見心地
- 自然さ
- 正式採用
- 表現の好み
- UIの実操作感
- 「これで十分」という製品判断

これらはPendingとして蓄積し、適切なBatchで返す。

レビュー待ちを理由に毎回ユーザーへ確認を返さない。
レビュー可能なまとまりになるまで蓄積し、まとめて提示する。

## 10. 現在のZEVへの適用

既存の人間未評価事項は `docs/HUMAN_REVIEW_PENDING.md` に移し、以後そこを生きた台帳とする。

今後の技術完了報告では、必ず次を含める。

- 新規Human Review Pendingの有無
- 追加したreview_id
- 既存Batchへ統合したか
- 人間レビューなしで正式採用へ昇格していないこと

## 11. 優先原則

最優先は、レビューを早く消化することではない。

**正しく蓄積し、正しい対象を人間に見せ、判断を正しい範囲へ反映すること。**

人間が常時張り付かなくても開発が進み、
必要な判断だけを後でまとめて返せる状態をZEVの標準運用とする。
