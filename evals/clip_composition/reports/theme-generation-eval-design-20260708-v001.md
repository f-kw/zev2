# テーマ生成評価 設計案

作成日: 2026-07-08
改訂日: 2026-07-09

## 目的

区間選択ではなく、上流の「どの切り抜きテーマを候補に出せるか」を測る。既存fixtureの人間ラベルを正解として使い、元配信単体の情報から同等テーマを候補に出せるかを評価する。

## 入力

入力は元配信単体から作れる情報だけにする。

- 元動画タイトル、URL、配信メタ情報
- 元動画のローカルSTT transcript
- 発話単位ID、時刻、話者、本文
- 元配信音声だけから計算できる補助信号を将来追加可能にする。ただし初期版ではSTT本文中心でよい

使ってはいけない入力:

- 切り抜き動画の情報
- expectedCuts
- DP照合結果
- 人間確認メモ
- 人間逆算テーマ
- 既存切り抜きのタイトル、説明欄、字幕

長尺配信の扱い:

配信全体を一度に入れられない場合は、モデルの入力上限に合わせて発話境界で分割する。分割は処理都合であり、採点上の重みにはしない。各窓で候補を出し、最後に重複をまとめる。窓の作り方、モデル名、入力文字数、候補統合の有無は結果に必ず記録する。

## 出力

テーマ候補N件をJSONで返す。Nは実験パラメータとして記録し、結果解釈時に固定する。

```json
{
  "generationSystem": "theme-llm-v001",
  "model": "使用モデル名",
  "params": {
    "temperature": 0
  },
  "sourceVideoId": "xxx",
  "themes": [
    {
      "themeId": "theme_001",
      "title": "短いテーマ名",
      "summary": "何が面白い、または見どころなのか",
      "whyItCanBeClipped": "切り抜きとして成立すると判断した理由",
      "sourceStartMs": 123000,
      "sourceEndMs": 153000,
      "supportingSpeechIds": ["12-47", 52, "55-60"],
      "representativeQuote": "元配信transcriptからの短い根拠",
      "riskNotes": [
        "前後文脈が必要",
        "説明だけでオチが弱い"
      ]
    }
  ]
}
```

時刻と発話IDは、テーマ候補の根拠範囲を後で区間選択へ渡すために使う。正解境界を当てる評価ではない。

## 正解データ

既存4fixtureのうち、1〜3件目は固定テーマを正解ラベルとして転用する。4件目は固定テーマが「まとめ動画全体の編成方針」であり、単一の元配信から導出できるテーマではないため、採用済み素材ブロックの章名を正解候補として使う。

| fixture | 型 | テーマ生成の正解ラベル | 妥当性 |
| --- | --- | --- | --- |
| UpRyakf5j80_clip_audio_v001 | 単一区間、境界精度検証型 | `登録者数世界2位扱いへの照れと順位変動への冷静な反応` | 元配信内の該当発話から直接導出できる見どころ。 |
| r_ztjHaHmcg_partial_material_v001 | 複数区間、短ブロック含む | `配信者が食べていける同接規模について現実的に答える場面` | 複数素材ブロックをまたぐが、同じ話題として元配信内発話から導出できる。 |
| aX-axQMWR3c_single_material_v001 | 長尺単一区間 | `Vの組織内あれこれ` | 組織内の関係性を話す長尺単一区間として、元配信内発話から導出できる。 |
| XauLZgnWHtA_part01_partial_material_v001 | 複数素材ブロック、除外範囲あり | `逆凸遊戯王`、`スタッフと相談`、`変態女装おじさん`、`拍手の音`、`実装から2年 朝4時`、`取りたい資格` | 固定テーマの `4. 【2023年6月①週】...` はまとめ切り抜きの編成名で、単一元配信からは導出不能。採用6ブロックの章名は、それぞれの元配信内発話から導出できるため、テーマ生成の正解候補として使う。 |

正解ラベルはモデル入力に使わない。採点時にだけ、候補テーマと意味が同じかを判定する。

## 採点

採点は二段に分ける。

一段目は機械判定で、候補の根拠発話範囲がexpected区間と物理的に重なるかを見る。これを範囲hitと呼ぶ。候補の `sourceVideoId` がexpectedと異なる場合は、時刻が重なっていても範囲hitにしない。範囲hitが1件もないfixtureまたは正解ラベルは、その時点で自動失敗にする。

二段目は人間判定で、範囲hitした候補だけを見て、正解ラベルと意味的に等価かを判定する。範囲hitしていない候補を人間判定へ回さないことで、目視負荷を増やさず、元配信内の別場所をそれらしい言葉で当てた候補を混ぜない。

判定の段階:

1. 候補の根拠発話範囲が、正解素材区間と重なるかを機械判定する。
2. 範囲hitした候補だけ、人間が正解ラベルと同じ見どころを指しているかを見る。
3. 広すぎる候補、別の話題、既存切り抜き情報の混入、根拠発話なしの候補を失敗として記録する。

意味的等価の扱い:

- 表現が違っても、同じ場面の同じ見どころを候補化していれば成功。
- 正解を含むが広すぎて「何を切るか」が定まらない候補は、部分成功ではなく「過広範囲」として分ける。
- 似た語を使っていても、別の会話や別の笑いどころを指している場合は失敗。
- LLM judgeを使う場合でも、最終判定は人間が行う。LLM judgeには候補と正解ラベル、該当transcriptだけを渡し、判定理由を短く出させる。

記録する項目:

- `generationSystem`
- プロンプト版
- モデル名
- パラメータ
- 入力分割方法
- 候補数N
- 範囲hitの有無
- 範囲hitした候補ID
- 範囲hitなしによる自動失敗
- 根拠発話範囲の重なり
- 意味的等価判定
- 過広範囲、過狭範囲、別話題、根拠なし、入力漏えい疑い

## 区間選択評価との接続

初期はテーマ生成だけを単独評価する。テーマ生成に失敗している状態で区間選択まで通すと、上流で正解ラベル相当のテーマが出なかった失敗と、compositionが候補から選べなかった失敗が混ざる。

接続は次の順で行う。

1. 4fixtureでテーマ候補が正解ラベル相当の見どころを含められるかを見る。
2. 成功したテーマ候補だけを `llm-v012` の区間選択入力に渡し、既存expectedCutsへ届くかを見る。
3. テーマ生成が一定して正解ラベル相当の候補を含むようになった後に、テーマ生成から区間選択までの通し評価を測る。
4. 通し評価で失敗した場合は、テーマ不在、テーマ過広範囲、composition選択失敗、境界精度失敗に分けて報告する。

## 当面の基準

区間選択側は `llm-v012` を基準にする。v012は判断方針を変えず、出力契約だけを圧縮して途中切れを減らした版なので、テーマ生成評価と接続するときにcomposition側の変数を増やしにくい。

5件目fixtureは保留する。テーマ生成評価で、既存4fixtureにない型が必要だと分かった場合だけ新規製造する。
