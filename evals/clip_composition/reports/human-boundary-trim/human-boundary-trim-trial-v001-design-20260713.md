# 人間による境界手直し試験 v001 事前登録

登録日: 2026-07-13

## UI校正による事前登録修正（正式計測開始前）

最初のcandidate 2で、人間は「4:13〜5:13が良い」と判断できたが、初版UIは時刻を直接入力できず、0.1秒・1秒・5秒ボタンと現在位置指定を要求した。UI内タイマーは開始ボタン後の60.686秒しか記録しなかったが、人間申告では内容判断を含め約3分かかった。

人間申告の3分×24候補=72分を、**候補絞り込みなし・単語境界スナップなしの1配信ベースライン**として固定する。72分は24件を実走した合計ではなく、最初の1件からの外挿値であることを明記する。

- candidate 2の4:13〜5:13は、人間が確定した校正境界として保存する。
- candidate 2は教師候補には含めるが、時間分布には含めない。
- v001で残る23候補を全件処理する計画は中止する。全候補処理自体が目標と不一致だからである。
- UIは開始・終了を`4:13`、`5:13`のように画面下へ直接入力できる形へ変更する。細かな現在位置操作は初期表示せず、必要な場合だけ開く。
- 次のv002は、candidate-ranking-v001の上位5候補だけを確認し、公開する3〜5本の仕上げ合計15分を測る。

## 1. 目的

接続標準`llm-v012@gemini-web-flash`が出した広めの仮区間を、人間が音・映像・間合いを確認して公開可能な境界へ直す負荷を測る。

この試験はAI単独の境界一致率を測らない。初版UIで1候補を判断した結果から、絞り込みなしでは1配信約72分になるという基準値を得た。候補単位の全件試験はここで中止し、次のv002では上位5候補から公開する3〜5本を仕上げる配信単位の時間を測る。

## 2. 対象の固定

- 素材は、承認済みプール内のホロライブ配信2本に固定する。
  - `nOEWCNc77MI_multiblock_material_v001` / 元配信 `YE-faluP7zY`
  - `9dtwF5Exu5w_multiblock_material_v001` / 元配信 `o8rZAhARXAc`
- 2026-07-12の接続本走で対象にした25テーマ候補を母集団とする。
- 1つの仮区間を開始・終了の2点だけで直せる24候補を、絞り込み前の母集団として固定した。candidate 2だけをUI校正で実施し、残る23候補の全件時間計測は行わない。
- 第二素材の候補16だけは、1仮区間が4正解へ対応し、2点調整では原理的に分割できないため事前に構造的対象外とする。失敗件数へ混ぜず、区間分割の課題として残す。
- 各候補の仮区間は、保存済みconnection-v001の`llm-v012@gemini-web-flash` run 1へ固定する。run 2/3から良いものを後選びしない。
- 24候補は当初の保存済みmanifest順を基準として保持するが、次の試験では元配信単体由来の順位付けで上位5だけを提示する。

この24候補は上流で範囲hitした開発データに条件付く。72分は1件の人間申告から24件へ外挿した比較基準であり、24件の実測分布でも、第二関門や第三関門の正式通過試験でもない。

## 3. 人間へ見せるもの・隠すもの

表示する:

- テーマ候補のタイトルと要約
- 元配信の映像・音声
- v012 run 1の仮開始・仮終了
- 人間が現在選んでいる開始・終了
- `分:秒`または`時:分:秒`で直接入力する開始・終了欄

表示しない:

- fixtureのexpectedCuts
- 既存切り抜きの境界
- boundary-v001の出力
- 境界差分や正解判定

人間への問いは「このテーマを単独で公開できる切り抜きとして、どこから始め、どこで終えるか」だけとする。

## 4. 計測

候補ごとに次を保存する。

- 計測開始から完了までの壁時計時間
- タブが表示され操作可能だった時間。タブ非表示中は別に記録し、主時間へ含めない
- 開始点を確定し直した回数
- 終了点を確定し直した回数
- プレビュー回数
- シーク・微移動・再生操作の回数
- 仮境界と最終境界
- 完了、判断不能、中断の状態と任意メモ
- 操作イベント列。各イベントには時刻、再生位置、その時点の開始・終了を保存する

主集計は完了候補の操作可能時間とする。平均、中央値、P90を並記する。P90は時間を昇順に並べた`ceil(0.90 × 件数)`番目とし、補間しない。壁時計時間、操作量、判断不能・中断は別表にする。平均だけで合否を決めない。

## 5. 最終境界の保存

- 人間が完了した境界は、既存fixture/expectedを変更せず、`human-adjusted-boundaries.json`へ別系統で保存する。
- 保存時に、確認者、確認日、元の生成系統、テーマ、仮境界、最終境界、操作時間、操作量を残す。
- このデータは将来のテキスト境界ルーターとboundary-v002の教師候補にできるが、自動で凍結fixtureへ昇格させない。

## 6. ハーネスの範囲

- `evals/clip_composition/`内だけに置く。
- 本体UI、API、DBは変更しない。
- ローカルの元配信をRange配信し、ブラウザで境界を決める最小構成とする。
- expectedCutsをハーネスへ読み込まない。試験完了後の診断時だけ別処理で比較できる。
- 途中保存は監査可能なJSONとし、既存評価結果を変更しない。

実行手順:

1. `node evals/clip_composition/prepare_human_boundary_trim_trial.mjs`
2. `node evals/clip_composition/serve_human_boundary_trim_trial.mjs`
3. `http://127.0.0.1:4317/`を開いて、時刻直接入力と単語境界候補が機能することだけを検証
4. 正式な時間計測はcandidate-ranking-v001の上位5が確定した後、v002の条件で開始する

## 7. 試験後の判断

1. v001は、1候補約3分・24候補約72分という絞り込みなし／スナップなしの比較基準として閉じる。
2. v002で、上位5候補の確認から公開3〜5本の仕上げまでを1配信単位で測る。
3. 第一・第二関門の時間条項は合計15分以内。候補単位の平均では判定しない。
4. 正式な第二関門判定は、配信者単位のdev/test分割と初見データで行う。

## 8. 固定した系統

- 接続標準: `llm-v012@gemini-web-flash` + テーマ根拠範囲の写し許容
- 入力選定: `input-selection-v004`（暫定標準、2素材で部分的汎化）
- boundary-v001: 実験版として保存。標準接続へ昇格しない
- 非発話シグナル: 音声・映像が正解境界を一貫して説明する別実測が出るまで保留
- テキスト境界ルーター: 人間の手直しログが蓄積した後の限定自動化候補
