# candidate-ranking-v001 reason-only設計

設計日: 2026-07-13

## 1. 採用理由

全89候補・60候補の机上検証で、チャット流速、根拠範囲長、笑い表記密度のうち、両素材で既存生成順以上のRecall@5を維持する信号はなかった。複数信号を結果後に混ぜず、次の単変数をテーマの意味判断へ移す。

## 2. 入力

配信1本分の全テーマ候補について、次だけを渡す。

- 候補ID
- title
- reason

チャット流速、根拠範囲、笑い表記、expected、切り抜き情報、照合結果は入力へ渡さない。機械信号は実走後の監査表へだけ結合する。

## 3. 問い

「この配信から最初に人間が確認する価値が高い候補」を上位5件まで順序付きで返す。

判断観点:

- 単独で内容が伝わる具体的な出来事か
- フリ、展開、反応または結論がreason内で説明されているか
- 同じ内容の重複候補ではないか
- 配信の通常進行だけを説明した候補ではないか

尺、チャット数、笑い回数へ独自の点数や係数を置かない。各候補へ合成点を返さず、順位と1文理由だけを返す。

## 4. 出力契約

```json
{
  "rankedCandidates": [
    { "rank": 1, "candidateId": 12, "reason": "最初に確認する理由" }
  ]
}
```

- 5件ちょうど
- candidateIdは入力に実在し重複しない
- rankは1〜5の連番
- 入力外の事実、時刻、数値評価を生成しない

## 5. 実走と採点

- モデル: `gemini-web-flash`
- run: 1。最初は上位5の上界確認であり、揺れ測定は順位付け方針が成立してから
- 素材: B素材89候補、第二素材60候補
- 生成系統: `candidate-ranking-v001@gemini-web-flash`
- 主指標: 全expected Recall@5
- 補助: 入力内expected Recall@5、Precision@5、重複候補数
- 比較: 既存生成順、各機械単独信号

## 6. 採否

- 両素材で生成順以上: 上位5を手直し試験v002へ使用する暫定候補
- 一方だけ改善: 素材依存として人間判断
- どちらかで悪化: 標準昇格なし

2素材は開発データなので、通過しても恒久標準や第二関門合格にはしない。
