## 1. 結論

同じ意味情報を一度だけ作り、その一つの内容から横型と縦型を出す初回実データrunの承認案である。形式ごとにGeminiへ同じ仕事を再実行させず、横型／縦型の改行・配置・crop・presetは出力側で分ける。

現時点の新経路は正式205件が`200/205`で、既存回帰、回帰後の既存3本tree照合、commit Aも未完了である。そのため、本書は将来の承認材料だけを先に整理したdraftであり、API通信・正式生成・描画の承認を求めない。

## 2. 目標への接続

このrunで確認するのは、ZEVが作る意味情報と、横型・縦型の見せ方を分離しても、同じ短尺内容を二形式へ一気通貫できることである。成立すれば、今後の無音・間の調整、遠距離接続、タイトル、演出を同じ意味情報境界へ追加できる。

## 3. 実行前の必須条件

1. 正式205/205と全ID入りTAP保存。
2. 既存合格gate 287/287。
3. 既知baseline 64/181のexact不変。
4. 回帰後の既存横型2本・縦型1本tree照合。
5. 27 file以内の実装をcommit Aと27 file SHA表で確定。
6. 使用素材、対象区間、横型style入力、縦型style入力、API支出上限を実行前下書きへ固定。

一つでも不成立なら、非公開本文を外部へ送る前に停止する。

## 4. 最小の実行案

| 段階 | 処理 | API通信 | 停止条件 |
|---|---|---:|---|
| 実行前 | 入力、二形式、支出上限を一枚で確認 | 0 | kawafmmが承認しなければ停止 |
| B5 | 固定payloadのtoken計測と上限判定 | countTokens最大2回 | 上限を保証できなければ生成前停止 |
| B6 | 意味まとまり終端を1回だけ選ぶ | generateContent 1回 | 無効・abstained・通信失敗なら停止 |
| ローカル | 一つの意味情報packageから横型・縦型を構築、描画、QC | 0 | どちらか不合格なら保存して停止 |
| 人間確認 | 完成した横型1本・縦型1本を目視 | 0 | 各形式を合否記録して停止 |

自動再試行は0回。生応答は解析前に保存し、trim、fence除去、修復、黙ったモデル変更は行わない。同じ回答を二形式で使うため、Gemini生成は最大1回である。

現時点では素材、固定payload、実測token、実行日の公式単価が未固定なので、金額を作らない。

## 6. 人間作業量

最小3判断とする。

1. 入力と支出上限を含む一括実行承認: 1件、目安1分。
2. 横型完成動画の目視: 1件、動画尺＋約30秒。
3. 縦型完成動画の目視: 1件、動画尺＋約30秒。

横型と縦型は同じ確認sessionへまとめる。行ごとの採点、JSON確認、大量照合は人間へ回さない。B5実測が事前上限内なら、その条件を承認文へ含めてB6まで連続させ、人間待ちを追加しない案を推奨する。
