## 5. 推奨する新計画

92件の機能検査と、違反codeの観測表を分離することを推奨する。

### 推奨案

1. 92件については、Node test runnerが実測した
   `ID / passed・failed / duration`の92行を生の検査結果として保存する。
2. `期待status / 期待code / 実測code`は、
   実際に一つの拒否枝を起動してcodeを観測する専用検査だけの表へ限定する。
3. 静的確認しかしていない検査を「code実測済み」と書かない。
4. 複数枝を持つ検査IDに、実装者が代表枝を選ばない。
5. H01〜H06、横型二層比較、正式preset登録の合格条件は維持する。
6. 保存済み正式成果物・fixture、処理結果byte、42ファイル上限は維持する。

この形なら、動画を作る機能の92件と、
失敗理由を実際に観測した範囲の双方を正直に残せる。
結果表のためだけに既存86検査へ観測装置を増築しないため、
「最終目標へ近づかない防御装置を作らない」というZEV憲法にも合う。

### 非推奨案

既存8検査fileへ観測hookを追加し、
複数枝の全てを別行へ分割して巨大な結果台帳を作る方法。

実装量と検査件数が増え、92件という固定数も再設計が必要になる。
縦型一本の正式化より検査統治の増築が主目的になるため推奨しない。
