## 2. 基礎映像生成器の結果

処理の意味:

- 実jobファイル、人間承認payload、元編集案、元動画のhashを照合する。
- 未解決編集が0件で、具体的な最終区間列がある場合だけ進む。
- 元動画を読み取り専用の作業用snapshotへ固定し、その同じbyteだけから映像・音声・検査結果を作る。
- 指定区間を並べ替えず、30fps論理frame単位で連結する。
- 元音声がある場合は、映像frameと同じ境界から音声sampleを取り、元の空白、区間順、左右channelを保持する。
- 成果物4件を一時領域で全検査した後、ディレクトリ単位で確定する。他processのlockは解除しない。

検査結果:

- 自動検査: **20/20合格**
- 固有違反コード: **24/24を意図した経路で発火**
- 30fps / 60fps、単一区間 / 空きを持つ複数区間を確認
- 44,100Hz / 48,000Hzの各1frame・2frame音声を確認
- 先頭と途中の音声時刻空白、異なる周波数を持つ非連続区間の順序、stereo左右channelを実PCMで確認
- 実job byteが無い直接実行、元編集案の実kind不一致、元尺を1ms越える端点、既存出力、symlink、別process lockを拒否
- 同じ論理入力を異なるjob ID・出力先で生成した決定性を確認

独立監査で修正した主な危険経路:

1. lock取得に失敗したprocessが他processのlockを消す可能性を除去した。
2. 元動画のhash検査後に元pathが差し替わる可能性を、固定snapshotだけを全工程で使うことで除去した。
3. ミリ秒端点がframe丸めで元尺内へ吸収される越境を、有理数比較で先に拒否した。
4. 元編集案の申告kindだけでなく、実JSONのkindを検査した。
5. 人工的なjob hash代用を廃止し、正式CLIが読んだ実byteを必須にした。
6. 長尺の全frame・packetを巨大JSONへ溜めず、逐次検査へ変更した。
7. 音声sample数だけでなく、source PCMとencode入力をbyte単位で再照合した。
8. 長時間処理中の親directory差し替えを公開直前の全階層・実体path再検査で拒否した。
9. Nodeのpath APIでは検査と再帰削除の間の競合を完全に閉じられないため、本番生成器の自動`rm`・`unlink`を0件にした。成功時はworking directoryと所有lock、失敗時は公開用一時先・working directory・所有lockを診断用に保持し、戻り値と失敗詳細へ場所を記録する。
10. 60fps・181frameの整数ms終端から最終global-even frameを選べるよう、decoded frame数を時間対応表へ束縛した。
11. AACのdecoder出力長を実音声終端と誤認しないよう、streamとpacketが一致する提示終端でcanonical PCMを物理的に切った。時計が欠ける入力をdecoded尺へfallbackしない。
