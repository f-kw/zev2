## 2. 副線1: 停止原因の静的切り分け

20件を個別の20問題として扱わず、契約・実装・検査の静的照合で、次の3根へ分離した。

### 2.1 module load時I/O検査の偽陽性

正常な実装は関数が呼ばれた後にだけfile I/Oを行うが、自作scannerがその遅延領域を正しく認識せず、module load時I/Oと誤認している。正常fixtureへ余分な実装不一致を付けるため、多数の検査が本来の担当段階へ到達する前に止まった。

### 2.2 不成立な子から全体不一致を推測する集計

一つのcontainer件数が不正な場合、正常な子だけの部分和を全体件数として比較し、直接不成立な箇所と全体件数の二箇所を返していた。

現行契約から、人間判断なしで次を導出できる。

- 子の値が不成立な間は、全体値を比較しない。
- 直接不成立な最小箇所だけを返す。
- 全ての子が正常で、全体合計だけが違う場合は、全体値の不一致を返す。
- 境界候補数の同型集計も水平確認する。

これは質問事項ではない。

### 2.3 3.38GBファイルの一括Buffer読込

監視treeには、約3.38GBの実ファイルが2件ある。現行処理が各ファイルを一つのBufferへ全量読込するため、Nodeの2GiB上限で停止した。

監視対象の除外・削除・hash省略は契約違反である。同じfile descriptorから全byteを分割読取し、同じSHA-256・全byte数・open前／直後／読取後のfile状態一致を保つ必要がある。

package側と意味回答側は同じ読取handle契約を使うため、版付き分割読取は両方へ適用する。packageだけを例外化して次工程へ同じ停止要因を残さない。この適用範囲は現行契約から導出できるため、人間への質問事項ではない。

静的原因分析のA-5はこの導出を記録している一方、同じ文書のB-2は同じ適用範囲を人間判断として重複掲載している。本朝報告ではA-5を正しい分類として採り、B-2は質問として採用しない。既コミットの原因分析は当時の記録として変更しない。
