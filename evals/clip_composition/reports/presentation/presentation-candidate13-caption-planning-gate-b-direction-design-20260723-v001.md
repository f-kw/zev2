次は、ゲートAの境界証拠を別の正式成果物として一度公開してから読み直す工程を挟まない。

新しいゲートB jobが、固定済みのゲートA jobを変更不能なbindingとして参照する。そのうえで、ゲートA runnerを再実行するのではなく、runnerと合成検査が共用する純粋な境界生成処理を安定snapshot上でメモリ実行し、既知hashとの一致を確認した境界証拠を、そのまま**source-onlyの意味分割入力パッケージ**へ封入する。これにより、ゲートA正式preflightの「1回だけ」という実行記録を変えず、機械が作る区切り候補とLLMが行う意味判断を分離したまま、初描画へ必要な経路だけを前へ進める。

1. 決定的処理が、354文字と205境界候補から、正解由来情報を含まない意味分割用のsource packageを一度だけ固定する。
2. Web版Geminiが、本文や時刻を作らず、境界候補IDを使ってテロップの行とまとまりを選ぶ。

## 4. 中間公開専用工程を置かない理由

ゲートAは、同じ入力から同じ境界証拠を決定的に再生成できることと、入力・実装・環境・証拠内部のhash整合を実証した。そこで観測された三つのhashを、ゲートBでは実行前の期待値として新たに採用する。

この証拠だけを独立した`segmenter-boundary-evidence/...`成果物として公開する専用機構を新設しても、意味分割の品質や初描画の正しさは増えない。一方で、専用schema、lock、回復処理、公開検査、独立CLIをもう一組持つことになり、本来の目的に対して工程が重くなる。

そこで、意味分割入力を作る工程が次を同時に行う。

1. 新しいゲートB jobが、固定済みゲートA jobと全入力の実byte hashを検査する。
2. ゲートA runnerを呼び直さず、runnerが使うexport済み純粋処理そのものを安定snapshot上で二度呼び、境界証拠をメモリ生成する。
3. ゲートAが実際に使う同じcheckerとreport validatorへ現在の証拠を通し、新しいゲートB用validation reportを作る。検査用の同等ロジックを複製しない。
4. 二つの生成結果がbyte単位で一致し、§3の三つのhashと一致することを検査する。
5. 合格した証拠と元文字だけから、モデル入力を作る。
6. 境界証拠・モデル入力・漏洩検査・来歴・validation reportを一つの入力パッケージとして一括公開する。

これにより、境界証拠の正本性を弱めず、中間物だけを運ぶ工程を省ける。

## 6. source-only入力パッケージ

本設計での`source-only`は、**正解由来情報を含まず、元発話と承認済みの固定表示契約だけを使う**という意味である。表示幅上限や最大2行は教師正解ではなく、認定済みプリセットを安全に使うための固定契約である。

モデルへ見せる内容は次だけとする。

- container ID。
- 元順に並んだ境界候補IDと本文。
- containerの全文。
- 各境界候補の表示幅。
- 一行の表示幅上限と、1テロップ1〜2行という承認済み表示制約。
- 全候補を順番どおり一度だけ使い、意味の読める短い単位へまとめるという仕事の説明。

モデルへ見せない内容は次である。

- 教師切り抜き、教師テロップ、expectedCuts、fixture、DP照合結果。
- 過去の人間評価、既存の表示計画、正解とみなせる分割例。
- 生のmillisecond、frame、sample値。
- candidate-rankingやG4〜G7の人間ラベル。
- 描画済み動画と比較結果。

B3で固定する`semantic-source-package`は、少なくとも次を別ファイルとして保持する。

1. ゲートAの純粋処理から再生成した境界証拠。
2. モデルへ渡す構造化入力。
3. モデル出力を元文字へ戻すための決定的な対応表。
4. allowlist方式の漏洩検査結果。
5. job・入力・実装・runtimeを束縛するmanifest。
6. ゲートAと同じchecker・report validatorによる、今回の生成結果のvalidation report。

package rootは、ゲートA jobが既に予約した次の`formalOutputPath`と完全一致させる。

`evals/clip_composition/outputs/presentation/segmenter-boundary-evidence/DmWu0jVQfTE-candidate-13-v001`

このroot内の境界証拠ファイルを、後段がpathと実byte hashで参照する**唯一の正式な機械境界証拠**とする。別の`semantic-source-package` directoryへ複製・ミラーを作らない。B3ではこのrootのpackage一式を固定した時点で停止し、同じbyteを確認する前にprompt作成やGeminiへ進まない。開始時にrootが既に存在すれば上書きせず停止する。したがって、承認済み設計が要求する「機械境界生成→モデル実走」の停止点と来歴は維持される。

B5で初めて、承認済みprompt全文と`semantic-source-package`全体のhashを束縛した`execution-payload`を作る。promptをB3へ混ぜず、境界証拠の固定とモデルへ送る文面の固定を別の停止点にする。

正式なfield型、未知fieldの扱い、採番、違反コード、CLI終了コード、原子的公開手順は、方向承認後の実装契約で一意に固定する。

## 7. 意味分割の出力契約

モデル出力は、containerごとの**行末境界候補ID**をcue単位にまとめたものだけにする。

概念形は次のとおりである。

```json
{
  "status": "complete",
  "containers": [
    {
      "containerId": "segmenter-container-000001",
      "cues": [
        { "lineEndBoundaryCandidateIds": ["…"] },
        { "lineEndBoundaryCandidateIds": ["…", "…"] }
      ]
    }
  ]
}
```

実装契約では次を固定する。

- `complete`と`abstained`以外を受けない。
- containerを元順に一度ずつ記載する。
- 一つのcueは1〜2行。
- 行末IDはcontainer内で厳密昇順。
- 最後の行末IDはcontainer最後の境界候補ID。
- 前の行末の次から今回の行末までを、決定的処理が連続範囲として展開する。
- 展開後に205候補と354文字が欠落・重複・逆順なく一度ずつ使われる。
- 一行が承認済み表示幅を越えない。
- text、時刻、理由、自由ID、スコア、未知fieldを受けない。

`abstained`、形式不成立、漏洩検査不合格の場合は停止する。同じ版の設定変更・自動再実行は行わない。
