## 3. 実行前に一枚へ固定する入力

1. 元配信と候補ID。
2. 使用する区間列。
3. 横型のpreset・幅・crop入力。
4. 縦型の型ID・preset・幅・crop入力。
5. API支出上限。

素材固有値をコードへ焼き込まず、全て版付きjobの入力として保存する。入力同士が承認済み契約と矛盾する場合は通信前に停止する。

## 4. 実行範囲

| 段階 | 処理 | API通信 | 停止条件 |
|---|---|---:|---|
| 実行前 | 入力、二形式、支出上限を一枚で確認 | 0 | kawafmm未承認なら停止 |
| B5 | 固定payloadのtoken計測と上限判定 | `countTokens`最大2回 | 上限内を確認できなければ生成前停止 |
| B6 | 意味まとまり終端を1回だけ選ぶ | `generateContent` 1回 | 無効・abstained・通信失敗なら保存して停止 |
| ローカル | 一つの意味情報から横型・縦型を構築し描画・QC | 0 | どちらか不合格なら保存して停止 |
| 人間確認 | 横型1本・縦型1本を目視 | 0 | 各形式の合否を記録して停止 |

自動再試行は0回とする。生応答は解析前に保存し、trim、fence除去、修復、黙ったモデル変更を行わない。Gemini生成は二形式合計で1回である。

## 5. 費用の扱い

素材と固定payloadが未確定なので、現時点で金額を作らない。

B5で、入力token、契約から導出した最大出力token、実行日の公式モデル・Standard単価・入出力上限を確認する。公式単価と整数token数だけで上限を計算し、独自係数や想定thinking量による補正を行わない。kawafmmが承認した支出上限を超える見込みならB6前に停止する。

## 6. 人間作業量

基本は3判断である。

1. 入力と支出上限を含む一括実行承認: 1件、目安1分。
2. 横型完成動画の目視: 1件、動画尺＋約30秒。
3. 縦型完成動画の目視: 1件、動画尺＋約30秒。

横型と縦型は同じ確認sessionへまとめる。行ごとの採点、JSON確認、大量照合は人間へ回さない。
