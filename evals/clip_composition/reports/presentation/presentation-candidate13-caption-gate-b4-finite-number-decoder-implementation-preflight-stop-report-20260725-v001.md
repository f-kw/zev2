## 1. 結論

承認済み設計の検査12は、次を同時に要求する。

1. 内部画面幾何fieldでは有限な指数表記を受理する。
2. 整数fieldでは指数表記を拒否する。

現在の厳密JSON解析処理は、有限数値profileで`1e0`を数値`1`へ復号する。復号後のexact schema検査へ渡る時点では、元のJSON tokenが`1`だったか`1e0`だったかを区別できない。

したがって、整数fieldの値検査だけでは次の二つが同じになる。

```json
{"lineCount": 1}
```

```json
{"lineCount": 1e0}
```

この状態で実装を続けると、承認済み検査12を黙って弱めるか、既存処理に無いpath別token解析を独自に追加することになる。どちらも停止条件に該当する。

### 2.2 既存解析処理

`presentation_caption_semantic_source_package_v001.mjs`の厳密JSON解析処理は、number tokenを次の順で扱う。

1. token文字列を読む。
2. 整数限定profileなら`.`または指数表記を即時拒否する。
3. 有限数値profileなら指数表記を許し、`Number(token)`へ変換する。
4. finite、negative zero、safe integer範囲を検査する。
5. 数値だけをobjectへ格納し、token文字列は保持しない。

この処理は現在、数値fieldのJSONPathを持たない。有限数値profileを使った後のschema検査は値とfield名を見られるが、token表記を見られない。

## 3. なぜ現在の専用schema検査だけでは足りないか

設計済みの専用入口は、既存の有限数値profileで復号した後、配置結果のexact schemaを検査する構造だった。

これは次を正しく分けられる。

- `lineCount: 1.5`は、復号後も小数なので整数fieldとして拒否。
- `wrapper.top: 833.2`は、有限幾何fieldなので受理。

一方、次は分けられない。

- `lineCount: 1`
- `lineCount: 1e0`

どちらも復号後は数値`1`であり、`Number.isSafeInteger`が真になる。

raw JSONへ別の正規表現を当てる方法は、文字列内の数字やescape、配列・objectの入れ子を正確に扱う第二のJSON解釈を作るため、二重実装禁止に反する。指数表記を全fieldで拒否する方法は、承認済み検査12の幾何field受理を変更する。

## 6. 選択肢

### 案A: path対応の数値token方針を既存厳密JSON解析処理へ追加

既存の一つのparserがobject keyと配列indexから現在のJSONPathを保持し、number tokenを値へ変換する前に、版付きの内部方針へ`path / token / value`を渡す。

- 整数field: 小数点・指数表記を拒否。
- 列挙済み幾何field: 有限な小数・指数表記を受理。
- 未知path: 拒否。
- B1整数限定入口と表示台帳固定4係数入口は既存挙動を維持。
- job、CLI、環境変数から方針を注入しない。

利点:

- 承認済み検査12をそのまま満たせる。
- JSON解析を二重実装しない。
- 「どのfieldのどのtoken表記を許すか」を一つのparserで判定できる。

追加で固定すべき範囲:

- parser内部のpath表現。
- object key／array indexのpath更新規則。
- 既存二profileの結果不変検査。
- 専用配置方針の入口と非公開範囲。

### 案B: 内部配置結果では指数表記を全fieldで拒否

配置検査が現在`JSON.stringify`で出す通常小数だけを受理し、指数表記は幾何fieldでも拒否する。

利点:

- path対応parserへの変更が不要。

欠点:

- 承認済み検査12と契約を変更する。
- 非常に小さい／大きい有限幾何値を`JSON.stringify`が指数表記にした場合、正当な内部結果を拒否する。

### 案C: 整数fieldで`1e0`を整数として受理

復号後の値がsafe integerなら整数fieldとして扱う。

利点:

- 現在の専用schema検査だけで実装できる。

欠点:

- B1で維持してきた「整数fieldは整数tokenだけ」という字句契約と、承認済み検査12を弱める。
- 同じ整数意味のfieldが工程によって異なるtoken契約を持つ。

## 7. 推奨

**案Aを推奨する。**

理由は、承認済みの三領域を変えず、検査12も維持し、JSON解釈を一つに保てるためである。変更は既存parser内部のpath追跡と、配置結果専用の固定方針に限定できる。

ただし、これは現設計の「復号後にexact schemaを検査する」だけの実装より範囲が広い。承認なしに実装しない。
