# STT照合とfixture化手順 v001

この手順は、バズった切り抜きから切り抜き区間選択評価のfixtureを作るためのものです。本体UI、API、キュー、DB、承認ゲートには接続しません。

## 前提

- 切り抜き側の音声にはBGM、SE、字幕読み上げに近い誤認識、切り抜き師が追加したナレーションが混ざる可能性がある。
- 切り抜き側のSTTに、元配信には存在しない発話や音がテキスト化されることは正常な失敗として扱う。
- 照合でマッチしないチャンクが出ても、それだけでfixture候補を捨てない。
- 切り抜きは複数箇所を飛び飛びにつないでいる可能性がある。
- 切り抜きが複数の元動画をまたぐ可能性もあるため、結果を見るときに「1本の元動画に決まるはず」と仮定しない。

## 手順1: 切り抜き動画をSTTする

保存済み切り抜き動画をSTTする。

対象:

- `evals/clip_composition/research/downloads/IMQYaT_RWRA/IMQYaT_RWRA.mp4`

注意:

- BGMとSEで認識率が落ちる前提で扱う。
- 元配信に存在しない追加音声やSE由来テキストが混ざる可能性を記録する。
- 後続照合で使うため、可能なら発話単位の開始時刻と終了時刻を保持する。

## 手順2: 元動画候補をSTTする

説明欄から抽出した元動画候補をSTTする。

第一候補の元動画候補:

- `https://www.youtube.com/watch?v=8uuQldLptRE`
- `https://www.youtube.com/watch?v=LBBRk8blLV0`
- `https://youtu.be/Rfsj5uHy_Bs`

必須条件:

- 単語レベルのタイムスタンプ付きで出す。
- 区間の秒指定精度はここで決まるため、発話単位だけでなく単語単位の時刻を残す。
- 長尺動画ではSTT時間がボトルネックになるが、ここは品質優先で待つ。

## 手順3: チャンク単位で照合する

切り抜き動画全体を1つの発話列として照合しない。先に切り抜き側を約30秒単位のチャンクへ分ける。

今回の第一候補は18.622秒なので、初回は1チャンクになる。ただし手順としては常にチャンク単位を正とする。

照合の流れ:

1. 切り抜きSTTを約30秒単位へ分割する。
2. 各チャンクのテキストを照合前に正規化する。
3. 各チャンクを、元動画候補3本それぞれの全域に対して探索する。
4. チャンクごとに、対応元動画、開始時刻、終了時刻、一致度、マッチしなかった理由を記録する。
5. 複数元動画にまたがる結果を正常系として扱う。

正規化:

- ひらがな化する。
- 数字表記を統一する。
- 全角半角差を統一する。
- 記号、笑い表記、伸ばし棒、相づちの扱いを記録する。
- 正規化で意味を消しすぎない。削った要素が照合失敗の理由になり得る場合は、削除前の文字列も保持する。

結果の見方:

- チャンク1から4が元動画A、チャンク5から6が元動画Bのような結果は正常。
- 切り抜き師追加要素やSE由来テキストは、対応なしとして扱ってよい。
- 一番似ている1箇所だけを採用しない。チャンクごとの対応結果を見る。

## 手順4: 音声確認してからexpectedCuts候補化する

照合結果をそのまま正解として固定しない。STT照合候補に対して、先に音声比較を行う。

音声比較:

1. 切り抜き全体と元動画候補区間を比較する。
2. BGM、SE、編集で全体波形が崩れる前提で、発話部分だけの比較も行う。
3. 波形直接相関と音量包絡相関を記録する。
4. しきい値で自動確定せず、候補同士の相対比較と人間確認の根拠として扱う。

音声比較で元動画候補との対応が強く出た区間は、`audio_confirmed_visual_pending` として `expectedCuts` 候補にできる。この状態はcompositionプロンプト評価には使える。目視確認は最終データセットQAとして残す。

## 手順5: 最終QAとして目視確認する

必須確認:

1. 逆引きされた元動画区間を実際に再生する。
2. その区間が切り抜き動画の元ネタであることを目視と聴取で確認する。
3. 対応が曖昧な場合は、期待区間に入れず保留にする。
4. 確認済み区間は `visualVerification.status` を更新し、必要なら開始位置と終了位置を修正する。

`expectedCuts` には、開始時刻、終了時刻、人間の期待理由に加えて、チャンクごとの一致度を残す。

記録する情報:

- 元動画URL
- 元動画内の開始時刻と終了時刻
- 対応した切り抜きチャンク
- チャンクごとの一致度
- 目視確認したかどうか
- 目視確認した内容
- 照合に使わなかった切り抜き側の追加要素

理由:

- 1件目の正解データは以降の採点基準になる。
- ここに照合ミスが混ざると、その後の評価がすべて汚染される。
- 最初の数件は人間の目で品質保証する価値がある。

## 手順6: 人間が固定テーマを書く

固定テーマは、現行システムに生成させたテーマをそのまま使わない。

理由:

- テーマ自体が悪い場合、正解区間がテーマ候補の範囲外になる。
- その状態ではcompositionが正しく動いても、期待区間に到達できないfixtureになる。
- 今回の評価目的は、テーマが正しい前提でcompositionの区間選択力を測ること。

固定テーマの作り方:

1. 音声確認済みの正解候補区間を見る。
2. 「この切り抜き師は何をテーマとして切ったのか」を人間が1行で書く。
3. そのテーマに対応する代表発話と関連発話を、正解区間から逆算して固定する。
4. その固定テーマを評価fixtureの `themes.json` にする。

## fixture化の完了条件

- 切り抜き側STTが保存されている。
- 元動画候補の単語タイムスタンプ付きSTTが保存されている。
- 約30秒チャンク単位の照合結果が保存されている。
- 対応元動画が1本に限定されない前提で結果が記録されている。
- 音声確認済みの区間が `expectedCuts` に入り、確認状態が記録されている。
- `expectedCuts` にチャンク一致度が記録されている。
- 固定テーマは正解区間から人間が逆算して書いている。
