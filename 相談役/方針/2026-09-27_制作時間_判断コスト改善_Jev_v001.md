# 14. 制作時間・判断コスト改善

更新日：2026-09-27
位置付け：ZEVメイン計画の後続改善。5. 新素材Digest生成の実測を入口にし、制作時間・外部AI待ち時間・推論費用を下げる。Jevは中心候補だが採用前提ではない。

## 目的

新素材Digest 1本を作るのに時間がかかりすぎる問題を、感覚ではなく工程別実測で分解し、品質を維持したまま短縮する。

同時に、ZEV内のAI判断を「生成」「有限判断」「コードで決められる」に分け、有限判断のうちJev等へ置換すると効果が大きいものを実証する。

## 14.1 工程時間を固定する

5の初稿完成時に、少なくとも次を同じ実行記録へ保存する。

- 素材取得
- upload
- queue待ち
- Whisper文字認識
- alignment
- diarization（使用時のみ）
- transcript変換・検査
- Prospect候補探索
- Prospect採用
- 内部保持・表示範囲
- 字幕・境界
- 演出判断
- render
- QC
- 外部API待ち時間
- 全体wall time

取得できない工程を推定値で埋めない。queue待ち、計算時間、人間待ちを混ぜない。

各AI判断について、可能な範囲で呼出回数、入力規模、出力型、実時間、費用も記録する。常設dashboardは作らず、既存reportから開始する。

## 14.2 判断ポイントを棚卸しする

ZEV内のAI・外部サービス利用を次の3種類に分ける。

1. 生成が必要
   - 新しい候補の発見
   - テーマや理由の言語化
   - 要約や文章生成
   - Jev単独置換の第一対象にしない

2. 有限判断
   - yes/no
   - keep/drop
   - 候補選択
   - 順位
   - score
   - 有限preset選択
   - review要否
   - Jevの第一候補

3. 決定的コードで足りる
   - schema検証
   - 時刻・範囲
   - hash
   - QCの機械条件
   - AIへ寄せない

最初に確認する候補：

- Prospect候補の採否・順位付け
- Prospect内部の保持／削除判断
- 複数候補からのテーマ・構成選択
- 字幕の演出要否
- Normal / Color / Scale / Panel / Pulse / Bounce / Shake 等の有限演出選択
- 採用済み有限palette選択
- AI案を自動採用するか人間確認へ回すかのreview routing
- QCや問題候補の優先度付け

Candidate Discoveryのように新しい候補や説明文そのものを作る工程は、Jev単独置換の第一対象にしない。LLMが候補を生成し、Jevが有限判断・検証・順位付けを担当する分業は検証対象とする。

## 14.3 Jevをshadow評価する

本番経路を変える前に、保存済みの過去入力・判断結果と5の新素材結果を使い、Jevをshadowで再判定する。

比較項目：

- 現在のZEV/LLM判断
- Jev判断
- 人間評価がある箇所では人間結果
- latency
- call数
- cost
- confidence / probability

日本語、VTuber口語、否定、皮肉、反応語、前後文脈依存を含める。

一致率だけで採用しない。誤判定したときに動画内容を壊すか、見た目だけの軽微な差かを分ける。confidenceが高い誤判定も確認する。

## 14.4 最初の本番候補

失敗時の被害が小さく、効果を測りやすい有限判断から進める。

第一候補：字幕・演出の有限選択
第二候補：Prospect候補の採否・順位付け
第三候補：人間確認へ回すかのrouting

Prospectの発見自体や長文生成は後回し。

低confidenceや未対応入力では、既存LLMまたは人間確認へfallbackできる構成にする。Jevを追加した結果、二重判断で総時間が増える構成は採らない。

## 14.5 採用条件

同一入力で以下を比較して採否を決める。

- 品質が許容範囲を維持
- wall timeが実際に短縮
- 費用が低下、または速度価値に見合う
- 日本語で重大な系統誤りがない
- confidenceをroutingに使う場合、実データ上で意味がある
- 保存・再実行・監査可能
- provider障害時のfallbackが明確

メーカー公称の速度・価格だけでは採用しない。効果が小さければその判断ポイントは現行維持で閉じる。

## 14.6 ZEV以外への横展開

ZEVでJevの実証が成立した場合、現在利用している他サービス／AI workflowの「有限判断」も同じ基準で棚卸しする。

候補例：

- 分類
- routing
- ranking
- score
- review要否
- 候補選択
- keep/drop

具体的なサービスを先に置換対象へ決めない。

各サービスについて、

- 現在何を外部LLM/APIへ頼んでいるか
- 出力は文章生成か有限判断か
- 1回の遅延
- 費用
- 呼出頻度
- 誤判定時の影響
- 型付き判断へ落とせるか

を比較する。

ZEVで十分な実測が取れる前に、別サービスの移行プロジェクトを複数立ち上げない。ZEVを実証場にして、成功した判断パターンだけ横展開する。

## 14.7 終了条件

14は「Jevを導入したら完了」ではない。

- 5の工程時間表が完成
- 主要ボトルネックが順位付け済み
- 有限判断／生成／コードの棚卸し済み
- Jev shadow比較を優先候補で実施
- 採用／不採用を実測根拠で決定
- 採用品だけ本番経路へ反映・回帰確認
- 置換しない工程も理由を記録
- 8で別素材確認できる状態

までで閉じる。

Jev以外の改善が最大ボトルネックに効くなら、14内でそちらを優先してよい。Jev導入数を成果指標にしない。

## 外部確認

2026-09-27時点。

- TypeSafe公式はJevを、文字列生成ではなくtyped probabilistic decisionsを返すSystem One Modelとして説明。
- TypeSafe APIは yes/no、choice、score 等の構造化判断を提供。
- cclank/jevclip は字幕・文字稿を区間化してJevで価値判断し、動画ハイライトへ使う参考実装。ZEVへの適合証拠ではない。
